# Decisions

Choices made where SPEC.md was open or ambiguous. Newest at the bottom.

- **Timestamps are unix seconds (INTEGER) in SQLite.** Avoids driver-specific time parsing; the service layer converts to RFC 3339 UTC for JSON.
- **Go module path `github.com/AVMG20/bitploy`**, matching the GitHub repository; images are `ghcr.io/avmg20/bitploy`.
- **`BITPLOY_DEV=1`, `BITPLOY_APPS_SCHEME`, `BITPLOY_APPS_PORT`, `BITPLOY_LISTEN`, `BITPLOY_TRAEFIK_CONTAINER`, `BITPLOY_INTERNAL_URL` config vars** were added for local development (HTTP, `<slug>.localhost:8000`) and for wiring Traefik to bitploy.
- **auth-api: password hashing and token generation live in `internal/auth/passwd` and `internal/auth/tokens`**, not in `internal/auth` itself, because `internal/auth` imports `internal/app` (for `Actor`) and `internal/app` needs the hashing code. Hash format is a PHC string, argon2id m=19456 KiB, t=2, p=1; at most 4 hashes run at once to cap memory.
- **auth-api: login rate limit and API rate limit are in memory** (5 failures / 15 min per email+IP, 120 req/min per token as a token bucket). They reset on restart. The `/mcp` mount shares the per-token bucket with `/api/v1`. The 20 deployments/hour/user limit is left to the service layer.
- **auth-api: client IP** trusts `X-Real-IP`, then the first `X-Forwarded-For` hop, only when the TCP peer is loopback, private or link-local (Traefik); otherwise `RemoteAddr`. Behind Cloudflare, Traefik must be configured to put the real client IP in one of those headers.
- **auth-api: `/mcp` goes through bitploy's auth middleware first** (bearer only, never cookies; channel `mcp`; same 401 JSON shape; rate limit; 4 MB body limit). The MCP handler can read the actor with `auth.ActorFrom(ctx)` and still verify the token itself.
- **auth-api: CSRF** also applies to unauthenticated unsafe requests under `/api/v1` that carry an `Origin` header different from the public URL (stops login CSRF from app subdomains). Requests without `Origin` and without a cookie (curl) pass.
- **auth-api: audit pagination is by row id** (`AdminListAuditPage`, cursor `a:<id>`); `AdminListAudit(before time)` stays for the shared signature. Audit rows older than 90 days, expired sessions/invites and idempotency keys older than 24 h are pruned hourly by `RunAccountsMaintenance` (started in `cmd/bitploy`).
- **auth-api: extra service methods** beyond the stubs: `RevokeSession`, `UpdateEmail` (dashboard Settings sends an email with the profile), `AdminListAuditPage`, `RunAccountsMaintenance`. Extra REST routes implied by the dashboard: `GET /me/github-token` (removed later, see GitHub App below), `GET /apps/{app}/env`, `GET/DELETE /sessions[/{id}]`, `POST /sessions/revoke-others`, `PATCH /me`, `PUT /me/password`, `POST /apps/{app}/redeploy`.
- **auth-api: admin routes** are `GET /admin/users`, `PATCH /admin/users/{id}` (`{status?, quota?}`), `PUT /admin/quotas/{user_id}`, `GET/POST /admin/invites`, `DELETE /admin/invites/{id}`, `GET /admin/server`, `GET /admin/apps`, `POST /admin/apps/{app}/stop`, `GET /admin/audit`. They need a dashboard session (an admin API token is not enough).
- **auth-api: list endpoints over in-memory slices** (apps, tokens, sessions, templates, env, domains, users, invites) paginate with an opaque offset cursor; `ListDeployments` and the audit log paginate in the service/DB. `limit` above 100 is capped, not rejected.
- **auth-api: build log content type**: `GET /deployments/{id}/log` is plain text by default and `{"items": [LogLine]}` when the request sends `Accept: application/json`; `?follow=1` is Server-Sent Events (`: ping` every 15 s, `event: end` at the end). `GET /apps/{app}/logs` returns `{"items": [...]}`.
- **auth-api: suspending a user** sets the status first, then calls `StopAllForUser`; if that fails the error is returned (suspending again retries it), except `not_implemented`, which is only logged.
- **MCP instructions live in `internal/mcp/rules/instructions.md`, not `internal/mcp/instructions.md`.** `internal/app` (DeployRules, REST) needs the text and `internal/mcp` imports `internal/app`; a small `rules` package avoids the import cycle. A test checks the file equals the block in SPEC.md. The example address `https://<slug>.bitploy.nl` becomes `cfg.AppURL("<slug>")` and any other `bitploy.nl` becomes `cfg.AppsDomain`.
- **MCP tool results carry two text blocks**: the one-line summary, then the same JSON as `structuredContent`. Some clients only show text to the model, and without the JSON they would lose templates, logs and error hints. Tools have no output schema, so error results (`{code, message, hint, next_tool}`, `isError: true`) are not forced into the success shape.
- **MCP choice arguments carry a JSON schema enum** (`type`, `kind`, `window`) so the schema itself shows a model the choices; `stack` stays free text because the service answers an unknown one with `template_unknown` and the list. An optional argument sent as `null`, or as `""` where an enum applies, counts as left out. `wait_seconds` above 50 is clamped to 50, not rejected.
- **`/mcp` auth reuses the router's actor.** `mcp.Handler` wraps `auth.RequireBearerToken`; its verifier takes the actor `auth.Middleware` already put in the context, and only calls `svc.AuthenticateToken` itself when the handler is used on its own (tests).
- **`validate_dockerfile` takes an optional `app`** (slug) so the app's port setting and worker type apply; without it a Dockerfile with no EXPOSE reports `port_unknown`. Service method `ValidateDockerfileFor` does this; `ValidateDockerfile` keeps its signature.
- **Dockerfile checks use buildkit `instructions.Parse` on top of the `parser`** so unknown instructions and bad arguments (`FORM x`, bare `EXPOSE`) become `dockerfile_parse_error` with a line. Local stages (`FROM base AS x`) inherit EXPOSE, USER and HEALTHCHECK from the stage they build on. Base images that run as non-root by design (`nginx-unprivileged`, tags with `nonroot`, `cgr.dev/chainguard/*`) do not trigger `runs_as_root`, so the spec's static template stays free of warnings. `env_file_in_context` fires only when a COPY/ADD from the build context would actually include the file and `.dockerignore` (matched with `moby/patternmatcher`) does not exclude it. A `.dockerignore` that is listed in `Files` but not passed as content is trusted. No-Dockerfile with an unrecognised project falls back to the `generic` template.
- **Git sources**: HTTPS only, no credentials in URLs, the token goes only to github.com (basic auth `x-access-token`), clones go to a temp dir next to `dest` and are moved in after `.git` is removed, symlinks pointing outside the checkout are deleted, and connections to loopback/private/link-local/CGNAT addresses are refused (SSRF). Extra codes beyond the spec list: `source_url_invalid`, `source_subdir_invalid`, `source_subdir_not_found`. GitHub answers 401/404 alike for private and misspelled repos, so with no token that is `github_token_missing` and with a token it is `github_repo_forbidden` (both replaced later by `github_access_missing`, see GitHub App below); other hosts give `source_repo_not_found`. `deploy.GitSource.SettingsURL` (additive field) carries `PUBLIC_URL/settings` for hints; the deploy pipeline should set it when it calls `Clone`.
- **`remove_domain` and `stop_app` are annotated destructive**; `rollback`, `delete_app` too. Other writes set `destructiveHint=false` explicitly, because MCP defaults it to true.
- **`go.mod`/`go.sum` got `go get` additions** (go-sdk deps, `moby/patternmatcher`, buildkit parser/instructions deps, `google/jsonschema-go`); the integrator should run `go mod tidy`.
- **ops: apex domains.** A hostname is an apex when it is a registrable domain on the Public Suffix List (`golang.org/x/net/publicsuffix`, already in the module graph): `example.com` and `example.co.uk` yes, `www.example.com` no. Apex domains get A/AAAA records from `BITPLOY_SERVER_IPV4/6`; without server IPs they get a CNAME plus a note about CNAME flattening. Hosts under `BITPLOY_APPS_DOMAIN`, the public host and the edge host are refused (`domain_reserved`); a public suffix or unknown TLD is `domain_invalid`.
- **ops: DNS check.** Both 1.1.1.1 and 8.8.8.8 must show the TXT token (`bitploy-<32 hex>`) and a route to the server. "Route" means: a CNAME whose target is the edge host, or any address of the name equal to the server IP or to the edge host's own addresses (so longer CNAME chains and flattened apex records pass). A name that still resolves to Cloudflare's proxy ranges gets a "set it to DNS only (grey cloud)" error. Errors name the record and what was expected.
- **ops: a domain is `active` as soon as the route file is written** (no HTTPS probe). `issuing_cert` is stored first and stays if `SyncRoute` fails; the background checker (every 5 min) retries it. `ActiveHostnames` returns `issuing_cert` and `active`. A pending domain turns `failed` after its 48 hours; `check_domain` on a failed domain restarts the 48 hours. A passing domain whose DNS later breaks stays `active` and shows the problem in `last_error`. `add_domain` of an existing hostname on the same app returns it unchanged; web apps only (`domain_worker_app`).
- **ops: metrics math.** CPU % is computed from the cumulative counters between two 15 s ticks (not from the 1 s stream deltas), memory is usage minus `inactive_file` (`total_inactive_file` on cgroup v1), rx/tx are the growth of the summed interface counters per tick. During a swap the old and new container of an app are summed into one sample. `LatestSample` is live: CPU and memory over the last ~6 stream readings (about 5 s), network from the last tick; it falls back to the last tick when the stream has nothing newer than 10 s. The 1 h series ends with that live point, and the dashboard polls it every 3 s (only while the tab is visible), so the charts move between ticks without storing more samples. Running seconds per day (`usage_daily`) are booked at the same tick, capped at two intervals.
- **ops: rollups run hourly, not only nightly** (and once at start), because otherwise the 24 h chart would show up to a day of raw 15 s samples. Only complete 5-minute buckets are written and never rewritten. `GetMetrics` for 24 h and 7 d returns the rollups plus the newest not-yet-rolled-up raw samples folded into 5-minute buckets with the same function, so the series has one resolution. Rollup rx/tx are sums per bucket (bytes per 5 minutes), CPU and memory are averages with max columns.
- **ops: Docker events.** Only events of an app's current container (`deployments.container_name` of `apps.current_deployment_id`) for an app whose `desired_state` is `running` and whose status is `running` or `failed` are acted on, so a superseded container dying after a swap, a candidate failing its health check, or a user stop never flips the status. `die`/`oom`/unhealthy set `failed` with a message; when Docker restarts the container (`start`) the status goes back to `running`, keeping the "Out of memory" message so the owner still sees why. Crash loop (5 deaths in 5 minutes): the container is stopped, status `crashed` with the log tail in `status_message`, and `apps.desired_state` is set to `stopped` (query `OpsSetAppDesiredState`) so the reconciler does not restart it; then `SyncRoute` runs. `start_app` is the way out.
- **ops: nightly job at 03:30 UTC**: rollup, prune (raw > 24 h, rollups > 30 d, rows of deleted apps), image/volume sizes into `app_disk` (largest labelled image per app; volume by label, else by name `bp-<slug>-data`), `image prune` of dangling images carrying `nl.bitploy.managed=1`, build cache pruned to 10 GiB, `VACUUM INTO <data dir>/backups/bitploy-<UTC timestamp>.db` (newest 7 kept), audit rows > 90 d, uploads > 24 h (rows and zip files). The two Docker prune steps are skipped when `BITPLOY_DEV=1`.
- **ops: `ServerHasRoom`** sums the memory limits of all apps (stopped ones too, like the per-user quota) and always says yes where `/proc/meminfo` does not exist (macOS). `DiskHasRoom` checks the data directory's filesystem. `Service.ops` (an `opsState` value) is the one field added to `service.go`.
- **ops: compose and Traefik.** The compose network is named `bitploy` with the fixed subnet `10.201.0.0/24`, outside the app pool `10.200.0.0/16`, so the firewall can treat "app subnet" and "control plane" differently, and so Docker picks that network for Traefik's default route (lowest name). Traefik's static config is a file (Traefik ignores env vars when a file exists), so `install.sh` writes the ACME email into the installed copy. The default certificate (`tls.yml`) and the dashboard route live in the data dir's `traefik/dynamic/` as `_tls.yml` and `_dashboard.yml`, because the file provider watches one directory; the `_` prefix keeps them out of the reconciler's `Writer.List`. The dashboard route strips `X-Real-IP` (Traefik leaves it alone, so a visitor could forge it).
- **ops: firewall.** Rules live in their own chains (`BITPLOY-APPS` from `DOCKER-USER`, `BITPLOY-INPUT` from `INPUT`) rebuilt atomically with `iptables-restore --noflush`, so re-running changes nothing. Traffic inside one app /24 (Traefik joins every app network) is allowed by 256 explicit rules because the pool is split in /24 blocks; no `physdev` module needed. `systemd` re-applies it after Docker (re)starts. The probe test removes the rules once as a control run before asserting the blocks.
- **ops: the bitploy image runs as root** (documented in the Dockerfile and README): the docker.sock group ID differs per host and the socket is root-equivalent anyway. Base images: `docker:29-cli` (includes buildx), `golang:1.26-alpine`, `node:24-alpine`.
- **ops: backups.** `backup.sh` uses plain pipes into `restic backup --stdin` (not `--stdin-from-command`, which Ubuntu 24.04's restic 0.16 lacks) and `forget --group-by host,tags`. It takes its own `VACUUM INTO` copy with the `sqlite3` CLI (installed by `install.sh`), falling back to the nightly copy. `/etc/bitploy/bitploy.env` is deliberately not in the repository.
- **ops: `deploy/dev.sh`** builds on bash 3.2 (macOS) and creates a dev admin (`dev@bitploy.localhost`) on first run; `make dev` data lives in `./.data` with a stable dev secret key in `.data/dev-secret-key`.
- **Deploy (M2): one source snapshot per deployment, as a zip.** Inline files and uploads are stored as `data/sources/<deployment_id>.zip` (an upload is hard-linked from `uploads/<id>.zip`, which is deleted 24 h after use). Redeploy copies the snapshot of the current (else newest) files/upload deployment; only the current deployment's and the newest snapshot are kept. Git sources are cloned again.
- **Deploy: build slots are held for fetch, validate and build only.** The 2-slot limit (`BITPLOY_MAX_PARALLEL_BUILDS`) covers the build phase; a health check of 60 s does not block other builds. Per app only one pipeline runs at a time. Rollbacks need no slot. A queued deployment waits in SQLite, not in a goroutine, so a newer deploy cancels it cleanly.
- **Deploy: health check through a marker header.** The candidate router in the route file adds the response header `X-Bitploy-Candidate: <slug>`; a probe only counts when it sees that header, so Traefik's own "404 page not found" (route not loaded yet) is never read as "healthy". If the header never shows, the deploy fails with `proxy_unavailable` (a server problem), not `unhealthy`.
- **Deploy: `dockerfile_path` is relative to the source root; `context_dir` is the build context inside it** (git: inside the cloned subdirectory). The Dockerfile checks get the file list relative to the context.
- **Deploy: deploying a stopped app starts it** (`desired_state` becomes `running` at the swap). Stop cancels the queued and the running deployment of that app.
- **Slugs: no leading or trailing `-`.** Needed for a valid DNS label; the spec only lists the allowed characters.
- **Rename of a slug = short downtime.** Images are re-tagged, the database changes, then the old container, network and route file are replaced by the current image under the new names (a few seconds down). The old slug is reserved for the owner for 30 days. (Apps with a volume were refused at first; see "Storage is an allowance" below.)
- **Restart recreates the container** from the current image (so new env vars and limits apply); it does not run a health check. Env and resource changes apply on the next deploy or restart.
- **Reconciler never touches containers without the `nl.bitploy.app_id` label** (the Traefik container, integration-test helpers). It restores a missing container up to 3 times, then marks the app `failed`. It leaves `crashed` apps alone (crash-loop detection stopped them on purpose).
- **Kill -9 safety on Linux:** the `docker buildx` child gets `Pdeathsig=SIGKILL`, and the reconciler removes images no deployment row knows, so a build that finished after a crash leaves nothing behind.
- **Env var rules:** names `[A-Za-z_][A-Za-z0-9_]*` (max 128), max 100 per app, values max 32 KB; `PORT` and `BITPLOY_*` are reserved because bitploy injects them.
- **Volume ownership:** a fresh named volume is root-owned unless the image already has `/data` with the right owner; apps running as a non-root `USER` should `mkdir /data && chown` it in the Dockerfile. Not handled by bitploy.
- **integrator: swaps wait for Traefik.** Before a deployment is marked `running`, the route is pointed at the new container and bitploy waits (up to 10 s) until Traefik's internal entrypoint serves `live.<slug>.bitploy.internal` with `X-Bitploy-Upstream` equal to the new container, so the URL works the moment the agent is told it does.
- **integrator: restart/start/stop/rename wait up to 5 s** for a deploy pipeline that is wrapping up instead of failing with `app_busy` right after a deploy finishes.
- **integrator: client IP** is the right-most `X-Forwarded-For` hop that is neither private nor Cloudflare; `X-Real-IP` is ignored (it is passed through from trusted peers and can be forged).
- **integrator: Go package patterns** are `./cmd/... ./internal/... ./web` because `web/node_modules` contains a stray Go package.
- **security: idempotency is an allow-list.** Only POST `/apps`, `/apps/{app}/files|deployments|domains|rollback|redeploy` are stored and replayed. Everything else (`/tokens`, `/auth/*`, `/invites/*`, `/me*`, `/admin/*`, `/sessions*`, `/apps/{app}/uploads`, lifecycle POSTs) ignores `Idempotency-Key`: those responses hold credentials (raw `bp_` token, invite URL, one-time upload URL). Uploads simply create a new upload on retry. Stored bodies also pass through `apperr.Redact`.
- **security: the admin "read every app" override needs a dashboard session** (`LoadApp`: `IsAdmin() && Scope == ScopeSession`). An admin API token of any scope only sees the admin's own apps; `/admin/apps/{app}/stop` was already session-only (`RequireAdmin`), and `StopApp` through a token no longer reaches other users' apps.
- **security: login limits are reserved before the password is checked** (in memory, per process, so parallel bursts cannot exceed them): 5 / 15 min per email+IP, 30 attempts / 15 min per IP over all emails, 20 / hour per email over all IPs. Correct passwords give the IP and email reservations back (only the email+IP counter is reset), so normal use never eats the budget. Trade-off: an attacker with many IPs can lock one email out for up to an hour (20 failures); accepted, the owner can still use an already open session. `ChangePassword` and `UpdateEmail` share one 5 / 15 min budget per user, also reserved first.
- **security: signup and invite acceptance are limited to 5 attempts / hour per IP.** Wrong invite codes and real signups count; validation errors (short password, bad email) do not. A full limit answers 429 `too_many_attempts` with Retry-After.
- **security: open signup does not confirm registered emails.** With `BITPLOY_SIGNUP=open` an existing address returns 409 `signup_failed` ("could not be created with these details; log in instead if you have an account") instead of `email_taken`. Without email verification this cannot be fully hidden (any failure after valid input means "taken"), so it only removes the explicit confirmation; the per-IP limit caps enumeration. Invite flow keeps `email_taken` because invites are admin-controlled and the clear message matters there.
- **security: the argon2 queue is capped.** Four hashes run at once; at most 32 may wait (`passwd.MaxWaiting`). Beyond that `Hash`/`Verify` return `passwd.ErrBusy` and the API answers 429 `too_many_requests` with Retry-After 5. A busy answer is not counted as a failed login (the reservations are given back).
- **security: custom domains can be claimed over a stale claim.** If a hostname is held by another app in `pending_dns` or `failed`, `AddDomain` deletes that row (guarded by `status IN (...)` in the delete, in one transaction with the insert) and creates a new one. Audit rows: `domain.claim_replaced` (target: the old domain, with old and new app) and `domain.add`. `issuing_cert` and `active` stay `domain_taken`. Ownership is still proven only by the TXT record before activation. Two parties can displace each other's pending claim, but neither can block the one who controls DNS: the TXT token is an HMAC (key `BITPLOY_SECRET_KEY`) of the app owner's user id and the hostname, so re-adding gives the owner the same token and their TXT record stays valid, and `AddDomain` runs the DNS check right away, so a claim whose DNS already matches moves to `issuing_cert` at once and can no longer be replaced.
- **security: HTTP read deadlines are per route, on request bodies only.** JSON API bodies 30 s, `/mcp` 60 s, `POST /u/{id}` 15 min, via `http.ResponseController.SetReadDeadline`; requests without a body get none, and the deadline is lifted as soon as the body is read (an expired read deadline would cancel the request context of long-polls such as `?wait=50`, and SSE streams clear it explicitly). No server-wide `ReadTimeout`/`WriteTimeout`. `MaxHeaderBytes` is 64 KiB.
- **security: at most 10 concurrent `?follow=1` streams per user**, counted in memory; the 11th gets 429 `too_many_streams` with Retry-After 5 before any stream bytes.
- **security: changing the email needs the current password.** `PATCH /api/v1/me` with `email` requires `current_password` (400 `current_password_required`, 401 `invalid_credentials` when wrong; name-only changes need nothing). The email is applied before the name so a wrong password changes nothing. The dashboard Settings profile form shows a "Current password" field as soon as the email differs from the saved one and sends the email only when it changed.
- **Security audit: git symlinks.** `dropEscapingSymlinks` resolves every symlink with `filepath.EvalSymlinks` and removes it unless the final target is inside the resolved checkout (dangling and looping links go too); it repeats until a pass removes nothing, so chains like `x -> .`, `y1 -> x/..` cannot survive. Links that stay inside the checkout are kept (legitimate repos use them). Zip sources already reject symlinks.
- **Security audit: build path containment for every source kind.** Before building, `deploy.ResolveBuildPaths` resolves `context_dir` and `dockerfile_path` with `EvalSymlinks` and fails with `source_path_escapes` (or `source_context_not_found` / `source_dockerfile_not_found`) unless both stay inside the resolved source root; the build uses the resolved paths.
- **Security audit: isolated builder.** Builds run with `docker buildx build --builder bitploy --load` on a `docker-container` builder (container `buildx_buildkit_bitploy0`) attached to the Docker network `bp-builder`. That network takes a /24 from the app pool, so `firewall.sh` applies to build traffic (internet yes; host, metadata and private ranges no), and the builder cannot see the daemon's local images, so `FROM bitploy/<slug>:<n>` fails. Limits: `BITPLOY_BUILDER_CPUS` (default 2, as `cpu-period`/`cpu-quota`) and `BITPLOY_BUILDER_MEMORY` (default 6g, raised from 3g after a medium Bun + Vite build ran out of memory; memory = memory+swap). Buildx state is in `<data>/buildx` (`BUILDX_CONFIG`), so it survives recreating the bitploy container. `Builder.Ensure` runs before every build: creates the network if missing, keeps a builder that boots and has the same limits (hash in `<data>/buildx/bitploy-builder.opts`), otherwise removes and recreates it. Changing the limits therefore takes effect on the next build.
- **Security audit: builder housekeeping.** The `bp-builder` network carries the label `nl.bitploy.builder=1`, not `nl.bitploy.managed`, and the reconciler skips it and `buildx_buildkit_bitploy0` by name too. The nightly prune is `docker buildx prune --builder bitploy --all --force --max-used-space 10GiB` (via `Manager.BuildxPrune`); the old daemon-level build cache prune is gone. Rollbacks reuse images already in the daemon and need no builder.
- **Security audit: `base_image_forbidden`.** The Dockerfile check rejects `bitploy/*` (also with a Docker Hub host prefix, any case, through ARG defaults) in `FROM`, `COPY --from` and `RUN --mount from=`; local stage names are fine. Defence in depth on top of the isolated builder.
- **Security audit: port 8081 is reserved.** `firewall.sh` drops NEW TCP connections from the app pool to port 8081 before the same-/24 rules, because Traefik (internal entrypoint) sits in every app network. Traefik's own connections to an app listening on 8081 would be dropped too, so `port_reserved` is refused by the Dockerfile check and by `create_app`/`update_app`.
- **Security audit: volume quota.** `users.quota_volume_mb` is a limit per app volume. A new hourly job (`Manager.EnforceVolumeQuota`, also at start) runs `MeasureDisk` (Docker's verbose disk usage, volumes by label) and then: over the limit and desired state running -> `desired_state=stopped`, status `failed` with "The /data volume is over its N GB limit ... delete files from /data or ask an admin for a bigger quota, then start the app again", container stopped, route synced, audit `app.volume_quota_exceeded`; at 80% or more a running app with an empty status message gets "Warning: the /data volume is almost full ..." (removed again below 80%). Starting the app again without freeing space lets it run until the next hourly check. A quota of 0 or less means no limit.
- **Security audit: container capabilities.** App containers drop `ALL` and add back CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID, NET_BIND_SERVICE (`dockerx.AppCapabilities`), on top of `no-new-privileges`.
- **Security audit: volume ownership.** `EnsureVolume` adopts an existing `bp-<slug>-data` volume only when its `nl.bitploy.app_id` label equals the app's id (a volume with another or no label fails the start with a plain message). `DeleteApp` returns `volume_remove_failed` when Docker cannot remove the volume (not-found is fine); the app row stays so the delete can be retried.
- **Security audit: reconciler and queue.** The reconciler joins Traefik to the `bp-<slug>` network of every running web app it is missing from (a recreated Traefik would otherwise leave every app at 502). With less than 15% free disk, Deploy/DeployFiles/Redeploy/Rollback answer 503 `server_disk_full` before anything is stored or counted (the build step keeps its own check for disk that fills while queued). `checkServerRoom` fails closed (`server_room_unknown`) on Linux when the room check errors.
- **Instance id: every installation labels and filters its Docker resources.** A one-row `instance` table (migration `00050_instance.sql`, `Store.InstanceID` creates it on first use) holds a random id. `dockerx.Client.Instance` (set in `cmd/bitploy` and by the integration tests, which get a fresh database and so a fresh id) puts `nl.bitploy.instance=<id>` on every container, network, volume, image and the volume init container, and the reconciler, `ListManaged*`, `ManagedContainers`, the dangling-image prune and the event watcher ask the daemon for that label (and drop anything else that comes back). With an empty id they return `ErrNoInstance` and do nothing. Resources of another installation, or created before instance ids, are left alone; the reconciler logs how many exist once per process. Lookups by app id (`ListAppContainers`, `ListAppImages`: delete_app and orphan images of apps in this database) also accept unlabelled legacy resources but never another installation's. Restoring a backup restores the id with the database, so the restored installation keeps managing its volumes. Caveat: containers created before this change carry no instance label, so their die/oom events are not seen and the reconciler does not clean them up until the app is redeployed. The `bitploy` buildx builder and `bp-builder` network are per daemon and shared by design.
- **New volumes are made writable.** `EnsureVolume` reports whether it created the volume; for a new one `PrepareVolume` runs a throwaway `busybox:1.37` container (label managed + instance, no network, all capabilities dropped, read-only root, removed afterwards) that does `chmod 1777 /data`, because Docker creates volumes `root:root 755` and apps run as a non-root `USER`. If the image has its own `/data`, Docker copies that directory's owner onto the empty volume at first start, which wins. 1777 instead of a chown to the image user: it needs no image inspection and only this app's container ever mounts the volume. If the init fails the new volume is removed again so the next start retries. Volumes created before this change stay as they are.
- **Route removal nudges Traefik.** `proxy.Writer.Remove` rewrites `_catchall.yml` with unchanged content afterwards, because Traefik's file watcher on Docker Desktop bind mounts misses deletions (stopped or deleted apps kept answering 502).
- **Memory and CPU quota counts apps that run.** Only apps with `desired_state = running` and a current deployment reserve memory and CPU (`SumAppResourcesByUser`, usage totals and the server memory guard). `create_app` and `update_app` of a not-running app only refuse an app bigger than the whole quota; the full check (`memory_quota_exceeded`, `cpu_quota_exceeded`, plus server room) runs when an app starts consuming: queueing a deployment or rollback for an app that is not running yet, `start_app`, and again just before the container starts in the pipeline (several first deploys can be queued at once). `update_app` of a running app checks as before. The 10-app limit is now reachable.
- **Static sites are free of the memory and CPU allowance.** An app whose live deployment was built from one of bitploy's own nginx templates (`static`, `node-spa`, `node-static`; `deploy.IsStaticKind`; `static_build` apps are static from creation) uses a few MB, so it has fixed limits (64 MB, 500 CPU millis) and is left out of every quota sum (`SumAppResourcesByUser`, `OpsUsageAppTotals`: whoami usage, dashboard cards, `checkResourceQuota`). It still counts as an app and for storage. The host totals (`OpsSumMemoryLimitsMB`, server room check) keep counting the 64 MB it really reserves. A user's own Dockerfile never qualifies, even `FROM nginx`: it can run anything (`/docker-entrypoint.d` scripts). The source of truth is `deployments.build_kind` (migration `00140`), set when the build is planned (`validating`) and copied to a rollback from its target; "static" is read from the *current* deployment, so a rollback or a new deploy changes it with the version that goes live. There is no flag on `apps` to keep in sync. The pipeline decides the limits once the kind is known (`settleResources`) and writes them in the swap transaction: a static deploy sets 64/500, and a static site that is deployed from another kind of source gets the defaults (512/500) after the quota check (`memory_quota_exceeded` or `cpu_quota_exceeded`, deployment fails with a plain hint). Queueing a deployment only checks the quota in build mode `dockerfile`, where the result is certain; the other modes are checked by the pipeline. Migration `00160` marks the live deployment of apps in build mode `static` (and gives them 64 MB / 500 millis on the app row, effective at the next container start); apps in `auto` are not backfilled because nothing stored says which template they used. `update_app` refuses other memory or CPU values on a static site (`static_fixed_size`) and refuses `volume=true` (`static_no_storage`). Apps deployed before migration `00140` have no kind and count as normal until their next deploy.
- **Deploy health failures have three codes.** `out_of_memory` (next `update_app`), `app_crashed` (next `get_logs`; the app or worker exited right after starting) and `unhealthy` (never answered, answered 500 or more, Docker HEALTHCHECK) so a small model can pick the fix from the code alone. The localhost hint still replaces the hint when the log mentions localhost. `internal/mcp/results.go` treats all three alike (`healthFailure`). The text in `internal/mcp/rules` and SPEC.md still says "unhealthy and ..." and was not changed.
- **Audit: slugs cannot take bitploy's own hostnames.** `<slug>.<apps domain>` equal to the host of `BITPLOY_PUBLIC_URL` or to `BITPLOY_EDGE_HOST` is refused with 422 `slug_reserved` on create and rename, on top of the fixed reserved list; otherwise an app could get a router for the dashboard host and serve a fake login page there.
- **Audit: same `Idempotency-Key`, one run.** Requests with the same user and key are serialised in memory; a retry that arrives while the first is still running waits and then replays its stored answer. Per process, like the other limiters.
- **Audit: quotas checked inside the transaction too.** App count (`quota_apps`, `BITPLOY_MAX_APPS`) and deployments per hour are checked once up front for a fast answer and again inside the insert transaction (`_txlock=immediate` serialises writers), so parallel calls cannot overshoot. The token limit and domains-per-app are left as they are (session-only, resp. low impact).
- **Audit: uploads follow the disk rule.** `POST /u/{id}` answers 503 `server_disk_full` below 15% free disk, before writing anything; the upload stays pending and usable. Without it a stream of 95 MB uploads could fill the disk that the apps and the database share.
- **Audit: impossible logins fail early.** An email over 254 bytes or a password over 1024 bytes (the signup maximum) gets 401 `invalid_credentials` at once, without touching the login limiter or the audit log, so request bodies of a megabyte cannot pile up in limiter keys and audit rows.
- **Audit: redeploy of an app with no deployments at all** answers 409 `app_not_deployed` ("never been deployed", next `deploy_files`), the code `restart_app`/`start_app` already use. `source_gone` stays for apps whose deployments exist but whose stored source was removed.
- **Audit: an upload body that hits the HTTP size cap** (chunked, no Content-Length) answers 413 `upload_too_large`, not `upload_interrupted`.
- **Redeploy rebuilds the live version; MCP `deploy` with only app= retries the newest attempt.** REST/dashboard `redeploy` builds the source of the current deployment, following a rollback to the deployment it rolled back to (`source_gone` if that snapshot is missing, never other code). MCP `deploy` without upload_id and without a git source calls `RetryLatest`: the newest non-cancelled deployment's source, even a failed one, because the hints say "update_app, then deploy with only app=" after a failed deploy. Retention keeps the rolled-back-to snapshot.
- **No-argument MCP `rollback` goes to the newest version older than the live one**, versions told apart by image (a rollback row runs its target's image), so a second rollback never returns to the version just rolled back from.
- **The reconciler starts an exited current container of an app meant to run** (not only missing or dead ones): bitploy stops a current container only when the app is meant to stop, and `unless-stopped` does not revive a stopped container, so this covers a recreate-mode deploy interrupted by a restart. Crashed apps are still left alone.
- **Stopping, suspending and deleting cancel queued deployments before the running one** (and again after), so the dispatcher cannot start the next queued deployment in between.
- **Storage is an allowance, like memory and CPU.** `users.quota_volume_mb` is now the user's total storage (default 25 GB, set in `InsertUser` because the old column default is 5 GB), and each app has its own limit `apps.volume_mb` (default 5 GB, 100 MB to 1 TB, `create_app`/`update_app` `volume_mb`). Every app with the volume on reserves its limit, running or not, because the files stay (`SumVolumeMBByUser`, `storage_quota_exceeded`); turning the volume on or raising the limit is checked, lowering it below what `/data` last measured is refused (`volume_limit_below_usage`). `EnforceVolumeQuota` uses the app's own limit. Migration `00060` gives existing apps their owner's old per-app quota as their limit and moves owners still on the old default (5120) to 25600. Apps and `whoami` report `volume_mb`, `volume_used_mb` (hourly measurement) and the reserved total. Docker's local volume driver has no size limit, so the limit stays a soft one checked hourly.
- **Volumes keep their name; renaming an app with a volume is allowed.** `apps.volume_name` (unique when set) is the Docker volume mounted at `/data`, fixed at creation: `bp-<slug>-data`, or `bp-<app id>-data` when a renamed app still uses that name. Existing apps got `bp-<slug>-data`, which is what they already used. A rename leaves the volume alone, so the `rename_with_volume` refusal is gone. To restore a volume from backup after a rename, look up the name with `docker volume ls --filter label=nl.bitploy.app_id=<app id>`.
- **App files count towards storage.** The storage allowance (`users.quota_volume_mb`) also holds every app's own files, so a repo full of images costs what it takes. `MeasureDisk` records per app the kept images (the largest image in full, base image included, plus `Size - SharedSize` of each older kept version, so layers shared between versions count once) and the stored source snapshots (`sources/<deployment id>.zip`, new column `app_disk.source_bytes`, migration `00070`). Git sources are not stored, their files are in the image. `MeasureSoon` re-measures 5 s after each deploy and delete (at most once a minute) on top of the hourly run. Taken storage = /data limits of apps with a volume + measured app files; turning a volume on or raising it must fit (`storage_quota_exceeded`), and a new build (not a rollback) is refused with `storage_full` once taken storage reaches the allowance. Because usage is measured after the build, one build can go over; the next is refused. Apps and usage report `files_mb`.
- **Traffic: the read position is saved with the counts, so a restart does not count lines twice.** The `traffic_cursor` row (byte offset after the last complete line, plus a hash of the file's first 256 bytes to tell a new file from the old one) is written in the same transaction as the flush. On start the reader continues there if the file still begins with the same bytes and is not shorter; otherwise it starts at the top. Lines read but not yet saved when bitploy dies are read again. If a flush fails, the counts go back into memory (the saved position stays behind) and go out with the next flush; apps deleted in the meantime are dropped from the flush first. `serve` waits up to 5 s for the background jobs after the HTTP shutdown, so the traffic manager's final flush happens. `ClientHost` can be the raw `X-Forwarded-For` value, so the last entry is used as the client address.
- **Traffic: `window=today` for the Overview.** It returns today's totals and `visitors_today` only (no series or lists), so the Overview's "Visitors today" does not run the full 24 hour queries.
- **Traffic stats come from Traefik's access log, not from a script or a proxy in front.** Traefik writes every request as JSON (only the fields the stats need, no cookies) to `<data dir>/traefik/logs/access.log`, mounted into bitploy as well. `internal/traffic` polls the file every 5 s, maps `RouterName` to an app through a table built from the apps and their custom domains (reloaded every minute, and at most every 10 s when an unknown `app-…` router shows up; the dashboard, catch-all and ACME routers and anything on the `internal` entrypoint are ignored), counts in memory and flushes deltas to SQLite once a minute, or every 2 s for 20 s after any traffic request (`Manager.Watch`) so an open Traffic tab or Overview is seconds behind instead of a minute (one transaction per app, so a just-deleted app only loses its own counts). Traefik cannot rotate the file, so bitploy truncates it after reading once it passes 4 MB and nothing was added in between (always at 64 MB); it never truncates in the middle of a line, keeps a partial last line for the next poll, and a file over 16 MB at startup is read from its last 2 MB only.
- **Privacy: counts only, daily salt.** A visitor is the first 8 bytes of SHA-256(random salt of that UTC day + IP + user agent). The salt and the sets of hashes live in memory for the current and previous day only; nothing with an IP or user agent is ever written to disk by bitploy (Traefik's own file holds IPs until bitploy truncates it, a few minutes of traffic). Bots (user agent containing bot, crawl, spider, curl/, headless, an empty user agent, ...) count as requests but not as visitors, pages, referrers or 404 paths; they are counted on their own (`bots`). Traefik is told to drop query strings from the log (`accessLog.fields.queryParameters.defaultMode: drop`) and bitploy cuts them off again; paths are capped at 200 bytes, at most 500 distinct paths (the rest `(other)`) and 200 referrer hosts per app and day, and static files (.js, .css, images, fonts, ...) count in totals but not in top pages. Pages are GET requests answered below 400.
- **Visitors are unique per UTC day.** Hourly and daily rows hold deltas that are added up, so a restart in the middle of a day forgets the hashes and a returning visitor can count twice that day. Over several days the total is the sum of daily visitors; for 24 hours it is the smaller of the sum of the hourly visitors and of the two days' visitors (both overcount, the smaller is closer). The top lists work on whole UTC days, so for 24 hours they cover today and yesterday. Error rate is answers with status 500 or more as a share of requests; 4xx is shown next to it as a count (`client_errors`). Retention is 30 days, pruned hourly, except day totals: 61 days, so 30 days can be compared with the 30 before; the stats tables reference `apps` with `ON DELETE CASCADE`, so they go with the app.
- **Traffic: compare with the period before only when it was fully counted.** `previous` is the totals of the equal period before (the 24 hours before from hourly rows, else the days before). The current period ends partway into an hour or day, so the last hour or day of the one before counts for the same share (at 06:00 UTC, a quarter of that day), as if traffic were even within it; without that every morning would look like a drop. It is `null` when the oldest stored hour or day of any app is newer than that period's start (stats were pruned or bitploy did not count yet) or the app was created after it, so a half-counted period never shows as a big jump. The dashboard also shows no change when the previous number is 0. The error tile compares the error rate, not the count; the speed tile the typical answer time, where up is the bad direction.
- **Traffic: "Direct / none" and "Not found".** A page view without a `Referer` counts under the referrer `(direct)` (no host has parentheses), outside the 200-host cap so it is never dropped; a referrer from the site itself still counts nowhere, a malformed or non-web one neither. Non-bot requests answered 404 are counted per path in `traffic_not_found` (migration `00180`), any method, files included (a broken link to an image is worth knowing), at most 500 paths per app and day (the rest `(other)`). The lists show the top 10; `?list=` returns one list up to 500 rows for the dashboard's "Show all".
- **Traffic: page views and answer times per hour and day (migration `00280`).** Page views (what the top pages count, `(other)` included) get their own column on `traffic_hourly` and `traffic_daily`, so they have a series, a 24 hour total and a previous period (the top pages keep 30 days and no hours). Answer times come from Traefik's `Duration`, which `traefik.yml` already kept; no Traefik change needed. They are counted into 8 fixed buckets (`speed_0`..`speed_7`: under 50, 100, 200, 500 ms, 1, 2, 5 s, slower) rather than kept as numbers, so a row stays a row of counts, adds up over any period like the rest, and the median and slowest 5% can still be estimated (linearly inside the bucket; the open last bucket reports 5 s, shown as "5 s or more"). Only people's requests that reached the app count: no bots (an uptime check every minute would make every app look fast), no static files (fast and many), no 101 (a websocket's duration is how long it stayed open), and nothing Traefik answered itself (`OriginStatus` 0, like a 502 while the app is down). Long-polling and streaming answers still look slow; there is no way to tell them apart in the log. Hours and days from before the migration have no times and no page views; a previous period that straddles it compares against too low a number for one window.
- **Traffic tab: four tiles, plain words.** Visitors (with page views under it), Requests (with the bot share), Speed (typical answer time) and Errors are the clickable tiles that switch the chart; under them one visible sentence says what a visitor and a request are, since the difference was not obvious to users. Each chart has a one-line explanation. The 4xx count and the bot share moved into an "All N requests" card with three split bars (who sent them, how the app answered, how fast), and "Not found" became "Missing pages". Empty windows say which window is empty and offer the 30 days.
- **Country from `Cf-Ipcountry`, else DB-IP Lite.** A two-letter `Cf-Ipcountry` header wins (Cloudflare's `XX` and `T1` do not count). Otherwise the IP is looked up in DB-IP's free "IP to Country Lite" (CC BY 4.0, credited in the dashboard and README) in `<data dir>/geoip/dbip-country-lite.mmdb`, downloaded in the background at start and again when older than 30 days (this month's file, else last month's; tried daily, every 6 hours after a failure), read with `maxminddb-golang/v2`. `BITPLOY_GEOIP=off` skips the download and the lookup; without a database the country is "unknown". Direct visitors can fake `Cf-Ipcountry`; that only skews a country count.
- **The Traffic tab is for web apps; the Overview shows "Visitors today" instead of "Automatic restarts" for them** (workers keep the restarts cell and have no Traffic tab). A restart count above 0 shows as a muted line under "Running for".
- **/data backups are tar.gz files next to the database, made through a helper container.** `dockerx.PrepareArchive` creates (never starts) a `busybox` helper with the volume mounted read-only (pulling the image first if needed), and `Open` reads `/data/.` from it with `CopyFromContainer`: the slow parts happen before the app is paused; `ReplaceVolume` empties the volume with `find /data -mindepth 1 -delete` in a helper and unpacks with `CopyToContainer` (the /data folder itself keeps its owner and mode). The helpers refuse to run when the volume does not exist, so Docker never creates an unlabelled volume under an app's name. A running app is paused while its files are read and resumed at once after (always, with a context that cannot be cancelled, also on errors and at shutdown). The pause happens under the app lock, the same one deploys take to swap containers and the reconciler to restart them, and a backup gives way (`errDeployBusy`) when a deployment is in flight; a restore holds that lock from stopping the app until it is started again (`desired_state` stopped, so the crash detection and reconciler leave it alone). One backup, upload or restore per app at a time (in-memory lock, `backup_busy`); delete_app refuses while one runs and removes the backup files only after the database transaction committed. Backups and restores are asynchronous (202) and run on a context that ends at shutdown (`RunBackground` sets it and waits for them; `cmd/bitploy` waits up to 5 s); the dashboard polls the list. The restore result is in memory only (it can be dismissed with `DELETE /apps/{app}/backup-restore`), but a restore that is under way is recorded on the app row (`restore_backup_id`, `restore_safe_id`, `restore_resume`, set when the app is stopped and when the before-restore backup is ready, cleared at the end). **After a crash or restart** (`recoverAfterCrash`, at the start of `runBackups`): running backups become failed and interrupted, `*.tar.gz.tmp` files and `bp-copy-*` helpers are removed, paused app containers are resumed, and a restore marker is handled: without a before-restore backup nothing was changed and the app is started again; with one, it is unpacked again (trusted mode); if that is impossible the app stays stopped with a message on its page.
- **Every archive goes through `sanitizeTar`, in and out.** Entries are rewritten to plain headers: only directories, regular files, symlinks and hardlinks; no absolute paths or `..`; symlinks must be relative, may use `..` only at the start and not above /data; hardlinks only to a regular file earlier in the archive; nothing may be placed below a symlink or file; no duplicates; setuid/setgid dropped; no PAX records or xattrs (so no file capabilities) and no sparse files; at most 300,000 entries, names up to 1,024 bytes and 32 MB of names in total; names starting with `.wh.` are skipped because Docker's unpacker would read them as "delete". Skipped entries (`.wh.*`, devices) still count towards the entry cap and the byte budget, negative sizes are refused, the size check cannot overflow (`h.Size > max-used`) and the copy stops when the request's context ends. **Trusted mode** is for archives bitploy made from an app's own volume (kinds manual, scheduled, before_restore; used when making them and when restoring them): absolute symlinks are allowed (`/data/current -> /data/releases/1` is normal), a hardlink to a `.wh.*` file is left out instead of refused, up to 5,000,000 entries, and names are not kept in memory; writing below a link and `..` stay banned. Uploaded archives are always strict. Restoring first reads the whole file once without writing (dry run), so a damaged or invalid file is found before the volume is emptied. Uploads are recompressed from that clean stream, limited to the app's /data limit (file and unpacked size) and the owner's free storage. Uploaded archives carry user ids from somewhere else: after unpacking, files get the owner of /data, or, when /data belongs to root, are made readable and writable for everyone (the same idea as the 1777 mode). Backups made by bitploy keep their owners.
- **Backups count towards the storage allowance** (`storageTaken` adds `SumBackupBytesByUser`, rounded up in total). The allowance already holds the /data limits as reserved, so an owner whose limits fill it has no room for backups until a limit is lowered; the error says so. A manual backup or upload that does not fit is refused up front (no room left) or while writing (the file is cut off at the free space); an automatic one is recorded as a failed row with the reason, which also counts as that period's attempt. Because several backups (of different apps of one owner) can be written at once, the check is made again when a file lands: `commitBackup` takes one lock, re-reads the free space, then renames the file and records it, so concurrent backups and uploads cannot overshoot the allowance.
- **Automatic backups run at fixed times in UTC.** `daily` is 03:00 every day, `weekly` is Sunday 03:00. A backup is due when the newest automatic attempt is older than the latest such moment, checked every 10 minutes (first check 30 s after start), so a missed one is caught up and switching it on makes the first one at once. Apps without `/data`, without a deployment, whose volume does not exist yet, or whose owner is suspended are skipped without a record. Retention (`last` N, up to 100, or `days` N, up to 365; default last 7) applies per kind to automatic and before-restore backups, always keeps the newest of a kind, and never touches manual or uploaded ones. Failed rows are removed after 14 days. Due backups run in their own goroutines, at most 2 at a time, each holding its app's backup lock from the moment it is queued (so the next check does not queue it twice). An attempt that was cut short, because bitploy was stopped or restarted (`app_backups.interrupted`) or a deployment was in the way, does not count as the period's attempt and is tried again; a stop is never recorded as "took too long".
- **Restore makes a safety copy first and undoes itself on failure.** If the "before restore" backup cannot be made (no room, Docker error) nothing is touched. If unpacking fails after the volume was emptied, the safety copy is unpacked again; the message says whether the old data is back. If that fails too, the app is **not** started: it stays stopped, with the way out on its page (restore the "before restore" backup, then start it). If a container cannot be stopped, the restore is abandoned before the volume is emptied and the app is started again.
- **MCP gets `create_backup` and `list_backups`, not restore, on purpose.** Making and listing backups is safe and an agent can do it before a risky change. Restoring replaces every file in /data and stops the app, so it stays a human decision in the dashboard; `list_backups` reports the restore state, and the rules text tells the agent to send the user to the Storage tab. Downloading a backup needs the deploy scope or a session (the files are the user's data): a read-only token may list but not download.
- **GitHub App only; the personal access token is gone.** One GitHub App per instance replaces `users.github_token_enc`, `github_login` and `github_token_expires_at` (dropped in migration `00100`), `PUT/DELETE /me/github-token`, and the error codes `github_token_missing` and `github_repo_forbidden` (now `github_access_missing`, pointing at Settings > GitHub). Reasons: a token is long-lived and sits in a text box; the App gives per-repository, short-lived, read-only tokens and push events for free.
- **The app is created through GitHub's manifest flow, by an admin.** The admin never copies keys by hand. `redirect_url` is `PUBLIC/admin`, `callback_urls` and `setup_url` are `PUBLIC/settings/github`, `request_oauth_on_install` is on, `public` is true so any user can install it on their own account. Credentials are sealed with AES-256-GCM and AAD `github_app:<field>`. The admin page warns when `BITPLOY_PUBLIC_URL` is localhost, a private address or a dotless name, because GitHub cannot deliver webhooks there. In that case the manifest has no `hook_attributes` and no `default_events` (GitHub refuses a hook URL it cannot reach), the stored webhook secret is empty, every delivery fails the signature check, and `push_status` is `no_webhook`. Private repositories still work. Fixing the URL means disconnecting and creating the app again.
- **State is a sealed, expiring token, not a database row.** `{purpose, user id, expiry, nonce}` sealed with AAD `github-state`; `manifest` lives 10 minutes and `connect` 15. It is bound to the user, so a link cannot be completed in another account, and it is useless on another instance (different key).
- **Linking an installation needs proof, never just `installation_id`.** The OAuth code is exchanged for a user token, `GET /user/installations` lists what that user can see, and only installations in that list are linked. The user token is used once and not stored.
- **A link is limited to the user's own repositories unless the GitHub user owns the account.** Seeing an installation is not enough: an organization member, or a collaborator on someone's personal account, would otherwise get every repository it covers. At link time `GET /user` gives the GitHub login; if the installation is on that same personal account the link is unlimited (`limited = 0`). Otherwise `GET /user/installations/{id}/repositories` (user token, so GitHub returns only repositories the user can open) fills `github_user_repos`, and the picker, clone credentials and webhook pushes use only those. The list is a snapshot: it is refreshed by "Sync from GitHub" and cleared on unlink, on uninstall and on disconnect. Someone removed from an organization keeps what they had until then; admins should remove such users from bitploy.
- **"Sync from GitHub" is OAuth sign-in only.** GitHub's install page does not bounce back for an account that already has the app, so after a local disconnect the user could not reconnect. `connect {mode: authorize}` skips the install page, links everything the user can see and refreshes their repository lists.
- **Clone credentials: the app owner's own installation, else anonymous.** For a `github.com` repository, candidates are the owner's active installations whose account matches the repository owner (those that cover the repo first). The token is requested for that one repository with `contents: read`, cached until 5 minutes before it expires, and reaches git only as basic-auth for that clone. Nobody else's installation is ever used for your app.
- **Push matching is strict.** Tags and branch deletions are ignored; the repo is compared lowercase without `.git`; the branch must match; the owner must have linked `installation.id`; and the installation's account login must equal the repository owner (without this check a user with an installation could deploy their app from someone else's same-named repository). Webhook answers stay a fast `202` either way; a matching push that could not be queued (for example the hourly deploy limit) is audited as `github.push_not_deployed`.
- **Quick pushes collapse through the existing queue.** `queueDeployment` already cancels older queued deployments of an app, so a push only queues; the pipeline is serialized per app and builds the newest commit.
- **Webhook answers fast and does no work inline.** Signature before parsing, 5 MB cap, dedupe on `X-GitHub-Delivery` (kept 7 days), `202`. If handling fails the delivery id is removed so GitHub's redelivery is not mistaken for a duplicate.
- **Installation events keep the picture current.** `installation` (deleted, suspend, unsuspend) and `installation_repositories` (added, removed, selection changed) update `github_installations` and `github_installation_repos`; going from all to selected resyncs in the background. The picker also refreshes (1-minute cache), and for unlimited links cloning still tries every owner-matching installation whatever the table says, so a stale table cannot break a deploy. Limited links use only `github_user_repos`.
- **Push status is computed from the database.** `git_source.push_status` and `push_message` never call GitHub, so `get_app` and the dashboard stay fast and cannot fail because GitHub is down. They say whether a push will deploy, and if not, the one thing to do.
- **A git-linked app refuses uploads, and says how to change that.** `deploy_files`, `create_upload` and `deploy` with an upload id return 409 `git_source_linked` with a hint (push, or unlink with `set_git_source` `remove: true` or "Disconnect repo"). Mixing both would leave the source of the running version unclear. Apps that are not git-linked are untouched: uploads stay a first-class path and the MCP rules only prefer git when the project already has a GitHub remote.
- **Auto-deploy defaults on for GitHub, and is forced off for other hosts.** Only GitHub sends webhooks bitploy understands. Other hosts keep working as plain, manual git sources.
- **CSP `form-action` includes GitHub's web origin.** The manifest flow is a browser form POST to GitHub, which `form-action 'self'` would block.
- **Not done on purpose:** polling, PR previews, other hosts' webhooks.


## Password protection and Copy for AI

- **Password protection is Traefik's basicAuth, not a bitploy proxy.** Traffic still goes straight to containers, so apps keep serving while bitploy restarts. `apps` gains `protect_enabled`, `protect_username` and `protect_hash` (migration `00110`, query `SetAppProtection`). The route renderer (`proxy.Route.Auth`) adds one `app-<slug>_auth` basicAuth middleware (`removeHeader: true`, so the login never reaches the app, realm "Private app") to the subdomain router and every custom domain router. The `_candidate` and `_live` routers on `*.bitploy.internal` never get it: health checks send no login. `desiredRoute` is the only place that builds a route, so deploys, rollbacks, restarts and the reconciler all keep it.
- **The password is write-only.** Only a bcrypt hash is stored. It is in no API or MCP response, no audit row (the row says `password_changed: true/false`), no log and no error text; tests check this. The hash is also in the route file on the server's disk (Traefik needs it there); a bcrypt hash cannot be replayed as a login.
- **Hash: bcrypt at cost 8, not the default 10.** Traefik v3.7's basicAuth has no result cache: it checks the hash on every request that carries an `Authorization` header (a browser sends it for every page, image and script), and only merges concurrent checks of the same credentials. The cost is paid per request on the CPU that serves all apps. Measured here: about 20 ms at cost 8, about 80 ms at cost 10. Cost 8 is still slow enough that a leaked route file is not a quick win for an attacker, and the password is chosen by the owner with at least 8 characters. SHA1 (`{SHA}`) and apr1 are readable by Traefik but unsalted or weak, so they were rejected. Argon2 is not supported by Traefik. bcrypt hashes look like `$2a$08$...` and contain no `:` or `{`, which matters below.
- **Limits: password 8 to 72 bytes, username 1 to 64 of `A-Za-z0-9._@+-`.** bcrypt ignores everything after 72 bytes, so longer input is refused rather than silently cut. Traefik splits `user:hash` on `:` and parses every dynamic file as a Go template, so a `:` or `{{` in a username would break the entry or the whole file; the charset rules both out. Passwords never go into the file, only the hash.
- **Fail closed.** An app flagged protected but with no stored login (for example a damaged row) gets a middleware with a hash nothing matches (`proxy.NeverMatchHash`), not an open door.
- **Turning it off forgets the login.** Username and hash are cleared, so turning it on again asks for a password again. Changing the username or password while it stays on is the same call with `enabled: true`; a missing field keeps the stored one. Workers cannot be protected (`protection_needs_web_app`): they have no address.
- **One endpoint, one MCP tool.** `PUT /apps/{app}/password-protection {enabled, username?, password?}` (session with CSRF, or a token with the deploy scope) returns the app. MCP `set_password_protection` mirrors it, is idempotent, and its description says to call it only when the user asks; the rules tell the assistant to take the login from the user, or suggest one (a few words and a number) and say it once in its answer, since nobody can read it back later. `get_app`, `list_apps` and the App JSON report `protected` and, while it is on, `protected_username`.
- **401s from the prompt are not traffic.** A visitor gets a 401 before the browser sends the password, once per page load. Traefik answers that itself, so the access log has `OriginStatus` 0; a 401 sent by the app has the app's own status there. `traffic.ParseLine` marks the first kind `Blocked` and the manager drops it. This needs `OriginStatus: keep` in `deploy/traefik/traefik.yml` (Traefik drops it by default). Existing installs: run `install.sh` again (it restarts Traefik when `traefik.yml` changed). Until then the field is missing, nothing is marked `Blocked`, and the 401s count as 4xx errors; no data is lost or wrong beyond that. Checked against a real Traefik v3.7.17 with a rendered route file: no login and a wrong login give 401 with `OriginStatus` 0, the right login passes (the app sees no `Authorization` header), a 401 from the app has `OriginStatus` 401, `$2a$` and `$2y$` hashes both work, and the `-live`/`-candidate` routers stay open. `traffic.TestParseRealTraefikAuthLines` holds those log lines. Each request with a login costs about 20 ms of CPU; a request without one is answered in well under a millisecond.
- **Dashboard.** A Password protection card on the app's Settings tab: switch, username, password with show/hide, one line on who can sign in and that the password cannot be read again, and changing either without turning it off. A small "Private" lock next to the address in the app header. Turning the switch on only opens the form; the app stays public until Turn on. Turning it off asks first, since the app is public at once and the login is forgotten.
- **Copy for AI is a frontend feature on top of the existing APIs.** Buttons on a failed deployment (Deployments tab) and on the Overview's failed or crashed alert build a short text for an AI assistant: one line asking it to find the cause, fix it and deploy again; the app's slug, name and URL; the deployment id (`dep_...`) and number with what failed; the source (`git repo@commit, branch` or the upload); error and hint; then the last 70 lines of the log in a code fence. Ids and slugs are what bitploy's MCP tools take, so an assistant with bitploy connected can follow up with `get_deployment` or `get_logs`. bitploy's `next_steps` are left out: they repeat the hint and are written for the MCP agent mid-deploy. The log comes from the existing endpoints: the deployment log for a failed deployment (it holds the build, start and health check steps, and the app's own output on failure), the runtime log for a crash. From the Overview, an app whose newest deployment failed gets that deployment; otherwise the crash of the running version. The text says so if the log cannot be loaded. Environment variables are never fetched. Lines are cut at 400 characters and the fence is longer than any run of backticks in the log. Copying: the `ClipboardItem` is created inside the click with a promise for the text (Safari requires that; Chrome and Firefox 127+ accept it). Without it (plain http) the text is copied after it loads, which a browser may refuse; the button then says so, and keeps the text for a minute so a second click copies it inside the click.

## New app form and uploads

- **New app form: apps made in the dashboard use build mode `auto`; MCP and REST stay strict.** The SPEC said there is no auto-detect build path, and the Dockerfile rule is still the default: `apps.build_mode` is `dockerfile` unless an app opts in, so agents and scripts see no change. The dashboard creates apps with `auto` (Dockerfile, else `index.html` as a static site, else `nothing_to_build`) because people who upload a folder of HTML should not have to know what a Dockerfile is. One function, `deploy.PlanBuild`, decides for every caller (inline deploys, the pipeline, the dashboard's preview mirrors it in `web/src/lib/detect.ts`), so the browser can say "Detected: Static site" before deploying, and the server stays the authority.
- **An `index.html` next to a project marker is not a website.** `auto` serves static only when the stack detection says `static` (no `package.json`, `requirements.txt`, `go.mod`, `composer.json` and so on). A Vite or React project has an `index.html` at its root, and serving that source as the site would show a blank page; `nothing_to_build` says it is a project that needs a Dockerfile, and the override (Static site) is there for the rare case where it is a website after all. Names match exactly, as on Linux and in nginx; an `Index.html` or a `dockerfile` gets a "rename it" error instead of "not found".
- **The static plan injects `Dockerfile.bitploy-static` and a merged `.dockerignore` at validate time, never into the stored zip.** A rollback or redeploy repeats the plan from the unmodified source, so the decision is the app's current mode, not a frozen one. Injection uses `os.OpenRoot` so a hostile file name cannot escape the build directory, and the name is not `Dockerfile` so a user's own file is never overwritten.
- **A single page with any name is a website; the home page is a setting of the app.** People often have their whole tool in one file like `Planning tool v3.html`. In `auto` and `static` mode, after "Dockerfile" and "index.html at the top" fail, the only `.html`/`.htm` file at the top (after the wrapping folder is stripped, with no project marker next to it) is served at `/`. With several pages and no `index.html`, the dashboard shows a "Home page" select (guess: index/home/start/main, else the first by name) and stores the choice in `apps.home_page` (migration `00130`), set through `create_app`/`update_app` like `build_mode`. A column, not a field on the upload, so a redeploy, a rollback and the next "Upload new version" keep the same home page without sending it again. If a later upload lacks the chosen page, the normal rules apply (one page: that page), and with several pages it fails with `home_page_missing`; with several pages and no choice it is `home_page_unclear`. The page is served by copying it to `index.html` in the extracted build context in Go (`writeInjected`, via `os.Root`), never into the stored zip and never by putting the name into the Dockerfile or the nginx config, so spaces, quotes and unicode cannot inject anything; the original path keeps working, and a real `index.html` is never overwritten (the rule only runs when there is none). `dockerfile` mode, the default of MCP and REST, ignores all of this.
- **Redeploy and rollback use the app's current mode.** Changing the mode (the Upload new version dialog has the same "Build as" select) applies to the next build of any stored version.
- **Folders are zipped in the browser, without a dependency.** The server only takes a zip, and a folder drop must work with one click for people who have never made a zip. `web/src/lib/zip.ts` writes stored/deflate-raw entries (`CompressionStream`), UTF-8 names and a Unix mode, and checks the limits (95 MB packed, 500 MB unpacked, 20,000 files) before and while packing, so the message appears before a large upload. `internal/deploy/zip_browser_test.go` reads a zip made by that code (fixture `testdata/browser-made.zip`, made by `make-browser-zip.mjs`) with the server's reader. The browser does not expose executable bits, so files that start with `#!` and `.sh` files get mode 755 and everything else 644; anything else that must be executable needs a `RUN chmod` in the Dockerfile.
- **Folder uploads leave out junk and secrets**: `.git`, `node_modules`, `__MACOSX`, `.svn`, `.hg`, `.idea`, `.vscode`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `.env`, `.env.local` and `.bitploy`. The form says what was left out. A dropped `.zip` is sent as it is. A single wrapping top-level folder is stripped by the server (`ExtractZip`, strip on) for both.
- **Build types: the dashboard picks the build, never a Dockerfile.** `auto` reads `package.json` (dependencies and devDependencies), the first `next.config.*` for Next.js, and the file list, in this order: own Dockerfile; `@sveltejs/kit` (with `adapter-static`: static build, `build`, pages; otherwise Node app, started with `node build` when there is no start script, with `PROTOCOL_HEADER` and `HOST_HEADER` set so form posts work behind the proxy, and a warning in `Why` when `@sveltejs/adapter-node` is missing); `next` (`output: 'export'`: static build, `out`, pages; else Node app, with the `nextjs` template when the config has `output: 'standalone'` and the start script is `next start`, otherwise the node template with a build step and `next start`, `.next` owned by the unprivileged user); `@remix-run/*` (not `@remix-run/router`), `@react-router/dev`, `nuxt`, `@nestjs/core`, `express`, `fastify`, `hono`, `koa`, `@hapi/hapi`: Node app (without a start script: `remix-serve`, `react-router-serve`, `node .output/server/index.mjs` for Nuxt, or `node <main>`); `astro` (with `@astrojs/node`: Node app, `node ./dist/server/entry.mjs` with `HOST=0.0.0.0`; otherwise static build, `dist`, pages); `react-scripts`: static build, `build`, single page; `vite` with a build script and `index.html` at the top: static build, `dist`, single page, but a Node app marked `Unsure` when a start script exists; any other project with a start script: Node app; else `nothing_to_build`. Python, PHP and Go without a Dockerfile are unchanged. The browser mirrors it in `web/src/lib/detect.ts`; both are tested from one table, `internal/deploy/testdata/detect_cases.json`, so they cannot drift. A static build is `node-spa` (unknown paths load `index.html`) or `node-static` (real pages, 404 otherwise, `404.html` shown), both with `absolute_redirect off` because the 8080 nginx listens on must not appear in redirects. The output folder is the app setting `output_dir` (migration `00150`; empty: the default of the framework); it is written into a Dockerfile, so it is limited to plain names (`templates.ValidOutputDir`). SvelteKit with adapter-static is assumed to prerender every page: a SvelteKit single-page site (adapter-static with a `fallback`) would get a 404 for client-side routes and needs its own Dockerfile. The explicit modes `node` and `static_build` ignore a Dockerfile in the source like `static` does. Agents keep the Dockerfile path: the MCP tools do not take `build_mode`.
- **One upload endpoint for the browser, orchestrated by the client.** `POST /apps/{app}/upload` (raw zip) does `create_upload`, receive and `deploy` in one request, with the same checks and audit entries; the dashboard creates the app first (`POST /apps`) and deletes it again if the first deploy cannot be started, so a failed form leaves no empty app (if the delete also fails, the error links to the leftover app). The upload call runs the same early checks as `deploy_files` (build mode, Dockerfile) on the zip before it queues anything, so a source that cannot build is refused while the app can still be removed. A deploy that starts and then fails (a build error) is not rolled back: the app stays so the error and the log can be read.
- **Only apps that are not git-linked get "Upload new version".** `git_source_linked` is still the rule, and the dashboard hides the button for them; the way back to uploads is "Disconnect repo". GitHub apps cannot change build mode from the UI (detection happens at build time, server-side, and the error shows in the deployment).
- **No live check of whether an address is free.** The slug is validated locally with the server's rules (length, characters, reserved names, `bp-` prefix); `slug_taken` comes back on submit and is shown at the address field. A live check would be a new unauthenticated-style probe of other people's apps for little gain.
- **The dashboard says "your AI assistant" only where it fits.** `friendlyError` rewrites hints that point at MCP tools (quota and slug errors) into dashboard wording and hides hints containing tool names, so beginners never read `update_app`.
- **First-deploy progress is a card on the Overview, not a new page.** `DeployProgress` polls the deployments list (1.5 s while something is in flight) and shows the 7 steps, the error with its hint and the log tail, because `current_deployment` stays empty until the first swap.
- **Auto mode builds a Node project without a Dockerfile; `dockerfile` mode never does.** The server reads `package.json` (the dashboard reads it too, from the folder or the zip, only for the preview). A Vite site is a build script, `vite` in the dependencies and `index.html` at the top: Vite apps with their own server (SvelteKit, Remix, React Router) have no `index.html` there and are not served as files. Otherwise a start script runs the app with the `node` template, after the build script when there is one (all dependencies installed, `NODE_ENV=production` only after the build), so TypeScript, Next.js or NestJS projects start from built output. Laravel (`artisan`) and Django (`manage.py`) are not Node projects even with a `package.json`. Anything else stays `nothing_to_build`.

## /data file browser

- **Helper containers, never the app container.** Listing, download, upload, new folder and delete run in throwaway busybox containers that mount only the app's volume (no network, all capabilities dropped but the few file ones). Paths reach the scripts as arguments, never in the script text. A symbolic link anywhere on a path is refused (even though a link could only lead into the helper's own throwaway filesystem), and a link is deleted or replaced, never followed. Only the owner gets to the files, like backup downloads: an admin who can see another user's app cannot read its data. Changes take the backup lock and the app lock; the app is not paused, so the dashboard says to stop it before replacing a database file.

## SQLite viewer

- **SQLite runs in a helper container, in Go, in our own binary; not the `sqlite3` CLI.** The /data volume is not mounted by bitploy, so a database is opened in a throwaway container like the file browser's, but running a program, not a shell script: `bitploy db-helper` (a hidden subcommand), which reads one JSON request and prints one JSON response (`internal/dbview`). busybox has no `sqlite3`, the CLI's output is hard to make safe (quoting, blobs, big integers, truncation), and `modernc.org/sqlite` is already a dependency and CGO-free, so the same code is unit-tested against temp files without Docker. The request goes into the container as a file (`/req.json`, `docker cp`): an environment variable is capped at 128 KiB, and a row with a blob can be bigger. The answer is read from the container's log (json-file, 16 MB cap) like the file browser's; the helper caps its own answer at 8 MB (`result_too_large`; the console cuts the rows instead) and an integration test reads a 6 MB single-line answer.
- **The helper image is built locally, once per binary.** A container from busybox (`VolumeInitImage`) gets the static Linux binary through `CopyToContainer` and is committed as `bitploy/db-helper:<first 16 hex of the SHA-256 of the binary>`, with the labels of bitploy's other helpers (`nl.bitploy.managed`, the instance id, `nl.bitploy.db_helper`). A new bitploy binary gives a new tag, builds a new image and removes the older ones. The binary is `os.Executable()` on Linux (the production image is that static binary), else `BITPLOY_DB_HELPER_BIN` (it must be an ELF file); `deploy/dev.sh` cross-compiles it for the architecture of Docker's VM (`docker info --format '{{.Architecture}}'`: x86_64 is amd64, aarch64 is arm64, `CGO_ENABLED=0`) into `.data/bitploy-db-helper`. With none, the viewer answers `db_helper_unavailable` and nothing else is affected.
- **Run as the owner of the database file.** SQLite makes `-wal`, `-shm` and `-journal` files next to the database. If a root helper made them, the app (a normal user) could no longer open its own database. The helper starts as root with only SETUID, SETGID and the file capabilities (CHOWN, DAC_OVERRIDE, FOWNER, for a folder that only the owner can enter), looks at every part of the path (a symbolic link is refused, as in the file browser), reads the owner of the file, drops to that user and group (`setgroups`, `setgid`, `setuid`; the capabilities go with it) and only then opens the database. A file of root is opened as root (SQLite copies the owner of the main file onto the sidecars when it can). A WAL database in a folder its owner cannot write fails with `db_unreadable`, like the app would; an integration test checks that this is what happens.
- **The volume is mounted read-write, also for reads.** A read-only mount cannot work for a WAL database (SQLite writes `-shm` even to read). Reads use `PRAGMA query_only=1` instead, and the SQL console's read-only mode is the same pragma. SQLite's authorizer refuses ATTACH, DETACH, `load_extension`, and the PRAGMAs that switch that guard off or reach outside the file (`query_only`, `writable_schema`, `locking_mode`, `temp_store_directory`, ...); `VACUUM INTO` is refused by looking at the statement, because the authorizer is not asked about it (a plain VACUUM attaches a scratch database of its own, which is the one ATTACH let through). The console cuts the text into statements itself (comments, strings and `CREATE TRIGGER ... BEGIN ... END` bodies are understood) and runs them one by one on one connection, so the answer can say which statement failed.
- **A date column is read back as it is stored.** `modernc.org/sqlite` turns TEXT in a column declared DATE, DATETIME or TIMESTAMP into a `time.Time`, which comes out in another format than the app wrote. The grid selects such columns as `ifnull(col, NULL)`, which hides the declared type from the driver and returns the same value; the console runs a SELECT again wrapped in a CTE that does that when its result has such a column.
- **Timeouts, one writer, no copy.** Inside the helper: `busy_timeout` 5 s (`db_busy`), the whole request 15 s with SQLite's interrupt (`db_timeout`), all row counts of a schema together 2 s (then `null`). On the bitploy side the container is removed (killed) after 20 s and when the caller goes away. The helper has no network, 256 MB, 64 processes (a Go runtime needs threads), 1 CPU and a 64 MB `/tmp`. The app keeps running: file locks work between containers on the same volume, and the file is never copied out and back. Writes hold the app's backup lock for their duration (a second write answers `files_busy`, a backup cannot start and a backup does not read a database that is being changed); reads do not, and nothing waits for a deployment. While a restore runs both are refused, as in the file browser. Every write is audited as `db.write` with the app, path, table, the kinds of statement and the rows affected, never values or SQL; a console request that fails half way audits what it did before it failed.
- **Stale keys are caught by `match`.** Update and delete match by `_rowid_`, but a live app can delete and re-insert (reusing a rowid) and `VACUUM` renumbers tables without an INTEGER PRIMARY KEY. The grid therefore sends the values it showed (`match`), and the WHERE adds `col IS ?` for each; a key that exists with other values is `row_changed` (409). Values are compared as stored, so the date-column quirk does not matter here.
- **At most 3 helpers per app and 8 in total; a restore waits for reads.** A helper is a 256 MB container and its answer is decoded in bitploy. A request waits up to 2 s for a place and then answers `db_busy`. Reads are registered under the same lock that marks a restore as running, and the restore job waits (up to 30 s; helpers die after 20 s) until they are done, because a helper that closes the last connection to a WAL database checkpoints and deletes its `-wal` file. Writes are already excluded by the backup lock. The answer is still decoded into typed values (numbers kept as `json.Number`) rather than passed through as raw JSON, to keep the OpenAPI schema; the limit above bounds the memory.
- **A write request is audited whatever came of it**, with an `outcome` of `ok`, `error` or `unknown`; a console request that leaves a transaction open is rolled back and answers `transaction_open` instead of reporting success.
- **Choices where the contract was open.** `db_timeout` is 422. Row keys: the first of `_rowid_`, `rowid`, `oid` that no column shadows. Insert into a table without a usable key is refused (`not_editable`) because the answer needs the key. Numbers in request bodies are kept as written (`json.RawMessage`), so a bare integer beyond 2^53 is stored exactly instead of being rounded by a float. Extra error codes beyond the contract are listed in SPEC.md. The MCP tool `query_db` is annotated destructive (it can write), reads with a read token, and is not a "deploy" tool: only `write=true` needs the deploy scope.

## Admin database viewer

- **Read-only, always; no write mode at all.** bitploy's own database holds the accounts, tokens and encrypted secrets of every user. A SQL console that could write would be a way to make oneself admin, change a quota, or break the schema without a trace, and nothing in the dashboard needs it: every change has an API and an audit row. So there is no insert, update, delete or cell operation, `write: true` is refused with 400, and the authorizer allows only statements that read, on top of `PRAGMA query_only=1`. It is the same viewer code as for apps (`internal/dbview`) with a policy, not a second implementation.
- **Secrets are hidden by the SQLite authorizer, not by editing SQL or results.** Masking in the grid would still let a console read them, and filtering the SQL text can not be made complete (`substr(password_hash, 1, 3)`, `hex()`, a join, a view, a CTE, `json_object`, a WHERE that tests one character at a time). The authorizer is asked about every column read of every statement, however it is written, and `SQLITE_IGNORE` makes SQLite use NULL instead; a comparison with a hidden column is then false for every row, so it is not an oracle either. The list of columns is in one place (`controlSecrets`, `internal/dbview/secrets.go`), with a test that fails when a migration adds a column that looks like a secret (hash, secret, token, key, enc, password, credential, ...) and nobody classified it as secret or as safe; secrets whose names do not look like one (`uploads.id`) are on the list by review. Beyond columns: `sqlite_dbpage` shows the raw pages and is refused, and `sqlite_stat4` keeps samples of indexed values (an ANALYZE put an invite hash in it in a test), so its `sample` column is redacted.
- **A filter or sort on a redacted column is an error; a search skips them.** Answering with NULL-based results would look like an answer; the grid is told with `redacted: true` in the schema and `column_redacted` otherwise.
- **A process of bitploy's own binary, not in-process and not a container.** There is no volume to mount and Docker would not add isolation that matters (the file is bitploy's own), but in-process would put a hanging or memory-hungry query in the control plane's address space: SQLite's own heap limit does not count in this driver (`PRAGMA hard_heap_limit` is accepted and ignored), so a `hex(zeroblob(1e9))` would take what it wants. A child process gives the same limits as the helper container where they matter: a kill after the 15 s query time plus 5 s, a cap on the answer, an empty environment, a memory cap and a crash that stays in the child. `os.Executable()` makes it work on macOS (dev) and in the production container alike, with the same `db-helper` code. The memory cap is `RLIMIT_DATA` (1 GB) on Linux: `RLIMIT_AS` was tried first and the Go runtime does not survive it (it reserves address space at start). The process does not switch user (the files are bitploy's own); as root it drops SETUID and SETGID like the app helper, and as another user it does nothing.
- **Two at a time.** Each is a process up to 1 GB with its answer decoded in bitploy; a third waits up to 2 s and then answers `db_busy`.
- **Audited by kind, not by text.** A console run is `admin.db.query` with the kinds of statement, like `db.write` for apps: the SQL may contain what the admin was looking for, and the audit log is itself in this database. Browsing is not audited (it would fill the log with page turns).

## Cancelling a deployment

- **A user cancel reuses the stop/delete machinery and adds who asked.** `requestCancel` marks the deployment as cancelled on purpose (`byUser`, so `finish` does not mistake it for a shutdown), remembers the actor and cancels the pipeline's context. `finish` then sees `cancelReq` and, instead of the plain `cancelled` of stop and delete, stores the message, settles the app and audits `deployment.cancelled`. Stop, delete and a newer deploy replacing a queued one are unchanged.
- **Swapping is the point of no return, decided under one lock.** The pipeline calls `commitSwap` right before it sets `swapping`; a cancel after that is `too_late_to_cancel`, and a pipeline that was cancelled first never commits. Without that, a cancel racing the swap transaction could cancel the context in the middle of it and report an internal error on a deployment that half went live.
- **The state is `cancelled`, with `error_code` `cancelled` and the message "Cancelled by the user."** A new state would need every consumer to learn it; `cancelled` already exists and is already terminal, final and not counted as a failure (`failed` carries the hints, the audit row and the "3 failures" advice). The error object is there so the dashboard and assistants can say why; the next steps for it say it is not a failure.
- **The app status settles like after a failure, without the failure.** Queueing moves a new or failed app to `deploying`; after a cancel it goes back to `running` (a version is live) or `stopped`; a never-deployed app becomes `new`, or `failed` again (with that error) when an earlier deployment failed. Another deployment still queued or in progress keeps it `deploying`. A live app is never touched.
- **A build is stopped as a process group.** `exec.CommandContext` only killed the `docker` CLI. On Linux the cancel now sends SIGTERM to the group (the CLI and the buildx plugin; buildx then tells BuildKit to stop the step) and SIGKILL 5 s later. The integration test cancels `RUN sleep 117`, checks with `pgrep` that the docker process is gone and with `docker top` that BuildKit's step is gone too (about 50 ms in practice), and that the next deployment of the app runs.
- **The call waits up to 5 s.** The answer then usually says `cancelled`; if the pipeline is slower the deployment is returned as it is and the client polls. A deployment that is in progress in the database but runs nowhere in this process (a crash before the reconciler ran) is shown as it is: the reconciler ends it as `interrupted`, a cancel does not paper over that.
- **Owner only.** Not even an admin session may cancel somebody else's deployment (`LoadApp` with write): the others get `deployment_not_found`, like for rollback.

## Security fixes

- **Uploads waiting to be deployed are capped.** A zip sent to `POST /u/{id}` takes disk space that no quota counts until it is deployed, so `create_upload` (and the dashboard upload, which uses it) applies the deploy-rate and storage-allowance checks of `deploy` and refuses with `too_many_uploads` (429) while the user has 5 uploads that can still be sent (pending, URL not expired) or deployed (received in the last 24 hours). That bounds one user to about 475 MB of parked zips.
- **No cache mounts.** All apps build on one BuildKit builder and a cache mount's id defaults to its target, so `RUN --mount=type=cache` would share one cache between users. The Dockerfile check refuses it (`cache_mount_forbidden`, an error), also when the mount options cannot be read without build arguments. Secret and SSH mounts stay allowed: bitploy never passes `--secret` or `--ssh`, so they are always empty.
- **Static sites hide dotfiles.** The templates' `.dockerignore` uses `**/.env`, `**/.env.*` and `**/.git` so nested ones stay out of the image, and the nginx templates answer 403 for any path part starting with a dot except `/.well-known/`.

## One-click catalog, pre-built images and Dockerfile editing

- **The port can come from the image.** A web app with no port setting and no `EXPOSE` used to fail with `port_unknown` at validation. Pre-built images often declare their port only in the image config, so validation now reports the info finding `port_from_image` and the pipeline reads the port after the build. `port_unknown`, `port_ambiguous` and `port_reserved` are raised there, and the port is stored on the deployment so a rollback reuses it.
- **The catalog version is recorded when the deployment goes live.** Each deployment stores the catalog version it builds (`deployments.catalog_version`, migration 00191); the swap copies it to `apps.catalog_version`. A failed or cancelled update leaves the app on the version it runs, so the update is still offered and can be retried, and a rollback brings the old version number back with the old Dockerfile. `apps.catalog_id` is set when the app is created. An update is offered only when the catalog version is newer (compared part by part, numbers as numbers), never for a GitHub-linked app.
- **Migrations 00190 and 00191.** The catalog columns are in `00190_catalog.sql` and `00191_catalog_deploy_version.sql`, after the traffic migration 00180 that reached main first; goose refuses a lower version that is missing on a database that already ran a higher one.
- **The Dockerfile path is not joined with `context_dir`.** The Dockerfile editor and the catalog use `dockerfile_path` relative to the source root, as the pipeline does.
- **Catalog apps run as non-root.** Each Dockerfile ends with a `USER`, so `runs_as_root` does not fire and the /data volume (mode 1777) stays writable.
- **Uptime Kuma and Vaultwarden have `HEALTHCHECK NONE`.** Their images ship a health check that runs a script every minute, and a Docker HEALTHCHECK replaces bitploy's HTTP check, so each deploy would wait for the first run (60 s for Vaultwarden). bitploy's HTTP check on `health_path` is used instead.
- **The Dockerfile editor works on the newest attempt.** GET and PUT start from the newest deployment that was not cancelled (rollbacks followed to their source), like a retry does, so a Dockerfile that just failed can be fixed and the editor shows what was saved last. The copy keeps every other file byte for byte (stored entries are copied without unpacking). In build modes `static`, `node` and `static_build` the Dockerfile is not used, so the editor says so and PUT answers 409 `dockerfile_not_used`.
- **How the catalog was verified.** Docker cannot run containers on the build machine (no mount or unshare capability). Each image (linux/amd64) was pulled from the registry with its layers checked against their digests and unpacked; PocketBase's release zips were checked against the sha256 in the Dockerfile and in the release's `checksums.txt`; IT-Tools' files were copied onto the nginx image as the Dockerfile does. Each app was then started in a chroot as the Dockerfile's user with no new privileges and only Docker's default capabilities, an empty /data (mode 1777) and the image env plus bitploy's, and answered on its port and health path. Not verified: the Docker build itself, the memory limit (no memory cgroup; resident memory was measured instead: Actual Budget peaked at 380 MB, so it gets 512 MB) and the network sandbox. Arnotes 0.1.0 was checked the same way after an anonymous pull from ghcr.io, and further through its API: the first account became the instance admin, a 20 MB attachment came back byte for byte, a manual backup worked, and after a restart with `ARNOTES_ALLOW_SIGNUP=0` the data was still there and sign-up answered 403.
- **Arnotes runs with `ARNOTES_TRUST_PROXY=2`.** Traefik drops X-Forwarded-For from every peer but Cloudflare's ranges and appends the peer it sees, so a subdomain request arrives as `<client-written>, <client>, <Cloudflare edge>` and a custom-domain request as `<client>` alone; Arnotes takes the second entry from the right, or the only one when there is one, which is the real client on both paths and cannot be faked by the client (1 would rate-limit by Cloudflare edge address). This trusts every request from Cloudflare's ranges to carry the address Cloudflare saw, as bitploy's own traffic stats already do.
- **Arnotes has `HEALTHCHECK NONE` and its own snapshots off.** Its image checks `/api/ready` every 30 s, which would hold each deploy that long; bitploy checks `/api/ready` itself. `ARNOTES_BACKUP_INTERVAL_HOURS=0` because bitploy backs up /data and the snapshots in /data/backups would count against storage twice; a manual backup from the admin page still works, and the S3 off-site copy needs the interval set again. It gets 256 MB: the server peaked at 44 MB resident under 3,000 requests at 400 at a time and a 20 MB upload (uploads and restores stream to disk).
- **Each catalog entry fits the default memory quota on its own.** The test used to cap all entries together at the default 2048 MB, so every new entry had to take memory from the others although nobody runs the whole catalog. Now each entry asks for 64 MB up to the default quota; an account without that much left gets the usual `memory_quota_exceeded` error, and the API and MCP deploy accept a smaller `memory_mb`.
- **Catalog deploy accepts `Idempotency-Key`.** It creates an app, so a retried request must not create a second one.

## Extra app domains

- **Slugs stay unique across all domains.** The slug names the container, network, image, volume, route file, Traefik routers (and so the traffic stats) and the dashboard URL. Making it unique per domain would touch all of those. Only the Host rule and the URL depend on the domain (`apps.base_domain`, empty for the default domain, so existing rows need no backfill).
- **The certificate lives in the database, the files are derived.** The PEM certificate is stored as is and the private key sealed with the server secret (like env vars), so the nightly backup (database only) has it and a moved data dir is repaired at startup: `ApplyAppDomains` writes `<data dir>/traefik/dynamic/certs/<domain>.crt|.key` (0600) and `_certs.yml` on every start and every change. The files go below the dynamic folder because Traefik already mounts it (`/dynamic`), so existing installs need no compose change; Traefik's file provider reads subfolders but only `.yml`/`.yaml`/`.toml` files as configuration. A certificate must cover `*.<domain>` (checked with `x509.VerifyHostname`), match its key and not be expired; any certificate is accepted, not only Cloudflare's.
- **Certificates are chosen by SNI.** App routers keep `tls: {}`; Traefik picks the stored certificate whose names match and falls back to the default one (`_tls.yml`). A domain without a certificate therefore gets the default certificate. Cloudflare's Full mode accepts that (it encrypts but does not check the certificate), so the certificate is optional; only Full (strict) needs one, and the admin page offers it as an optional step.
- **Who may use a domain is checked in the service.** `pickAppDomain` runs in `CreateApp` (so also for catalog deploys and MCP) and in `UpdateApp` when the domain changes; admins (the owner's role, not the token) may use every domain. Keeping the current domain is always allowed, so taking access away does not strand an app. The insert or update re-checks inside its transaction that the domain still exists, and removal counts the apps on the domain inside its own transaction.
- **Validation.** An app domain is lower-cased, `*.`, a scheme and a trailing dot are stripped, it must pass the custom-domain hostname rules (real TLD, not a public suffix), must not be the dashboard or edge host, and must not equal, contain or lie under another app domain or an existing custom domain. Custom domains in turn may not lie under any app domain. When the dashboard lives directly under an app domain, only that label is reserved, and only on that domain.
- **Migration 00200.** `app_domains`, `user_app_domains` and `apps.base_domain`. `app_domains.key_enc` is redacted in the admin database viewer.

## Services and volumes (compose phase 1)

- **One code path, two layouts.** An app is `single` or `multi` (`apps.service_layout`). Every existing app is `single` and keeps the apps and deployments rows as its source of truth; the new tables (`app_services`, `app_volumes`, `deployment_services`) mirror them in the same transaction. The deploy, reconcile, restart, logs, metrics, backup and files code reads services and volumes through `appSpecs`/`depServices`/`pickService`/`pickVolume`, which synthesize the one service `app` and the one volume `data` for a single app. So nothing a single app does changed: its names, labels, log lines and error texts are the same as before (the migration test and the old tests check that).
- **Names use `_` between slug and service.** `bp-<slug>_<service>-<n>`, `bitploy/<slug>_<service>:<n>`, `bp-<slug>_<volume>`. Slugs and service names cannot contain `_`, so no multi name can equal a single name (`bp-shop-web-3` is slug `shop-web`). Rename rewrites both forms by prefix.
- **A config hash keeps unchanged services running.** sha256 over the image ID and the run spec (env sorted, network, aliases, limits, mounts sorted, command, entrypoint, healthcheck). Only `multi` apps reuse a container: a single app always gets a new container per deployment, as before. The hash covers env values, so the admin database viewer redacts `deployment_services.config_hash`.
- **The route points at the public service**; every service gets its name as a network alias on `bp-<slug>`. Services start in `depends_on` order (a cycle or an unknown name is an error that names the services).
- **Metrics are stored per service** (`metric_samples.service`, rollups keyed by service); app totals are sums at read time. Crash-loop detection counts restarts per container, so one crashing service is reported by name.
- **Errors an AI can act on.** New codes: `service_not_found` and `volume_not_found` (message lists the names, `details.services`/`details.volumes`, next `get_app`), and `set_per_service` (next `get_app`). (`services_not_buildable`, phase 1's answer to building a multi app, is gone since phase 2.) A single app accepts its own service name (`app`) and volume name (`data`) but never needs them.
- **API shape is additive.** `services` and `volumes` are always present on an app; `LogLine.service`, `Metrics.service` and `Backup.volume` only appear for a multi app, so a single app's responses only gained the two arrays.
- **Migration 00210** adds the layout column and the three tables with a backfill, adds `service` to `env_vars` (new primary key), `metric_samples` and `metric_rollups`, and `volume` to `app_backups`. Down sums rollups back per app.

## Compose apps (compose phase 2)

- **One Dockerfile with SQLite in /data stays the default.** `create_app` makes build mode `dockerfile`, which never runs a compose file; the deploy warns `compose_ignored` and names `update_app(build_mode="compose")`. The MCP instructions (rule 8) and the runtime contract tell the AI to use compose only for a project that already has a compose file it needs, and never to write one just to deploy. Compose is the extra door, not the recommended shape.
- **Auto-detection only on the first deploy of an `auto` app.** Several services (or one that the app's settings cannot hold) make it a compose app; one plain build service is mapped onto the app's own settings (context, Dockerfile, port, health path, environment as variables, /data) and the app stays `single`. Once something went live, the layout never changes by itself: changing what runs is always the user's explicit choice.
- **Single to multi is one way and keeps /data.** The single app's Docker volume is reused (not copied) by the file's volume at /data, else mounted at the public service's /data, else kept unmounted with a warning, so no file is lost and no copy can half-fail. Going back would mean picking which services to drop, so `set_per_service` refuses it; a new app is the way back.
- **Image services are pulled by the builder.** A one-line `FROM <ref>` build on the isolated builder pulls the image, so the daemon never pulls on an app's behalf and the base-image rules apply. The cost is an export and load; an image service whose reference is unchanged reuses the live image.
- **The stored spec is the rollback source.** `deployments.services_spec` holds the resolved services and volumes (`${VAR}` as markers, never the values of variables), so a rollback does not need the source or a compose parser, and `app_services` needs no build columns.
- **Unchanged services keep running.** The config hash uses the image fingerprint (layers and config without labels), so a rebuild that produces the same layers does not restart a database; a Postgres is not bounced on every push.
- **A bad compose file is a 200.** `POST /compose/validate` and `validate_compose` return `ok: false` with every issue (`code`, `service`, `key`, `message`, `hint`): an AI fixing a file needs all problems at once, not the first as an HTTP error.
- **Variables per service.** `set_env` takes `service`; shared variables (service empty) fill `${VAR}` and go to every service, service variables override them for that service. A single app only has shared variables (its own service name is accepted and stored as shared).
- **Every volume is backed up.** Scheduled backups loop over the attached volumes with retention per volume; the SQLite viewer and the backup upload limit are per volume.
- **Migration 00220** adds `apps.compose_path`, `app_services.run_user` and `working_dir` (compose `user`, `working_dir`) and `deployments.services_spec`. Build args and target are not stored per service: a build always re-reads the compose file, and a rollback uses the stored spec.

## Projects and service templates (compose phase 4b)

- **Every app is in a project.** Migration 00240 backfills one project per app (`prj_<app id suffix>`, named after the app, alias = slug), so nothing that worked before needs a project. `create_app` without `project` makes an automatic project (`projects.auto = 1`) that is deleted with its last app or when that app moves out; a project made with `create_project`, renamed, or picked on `create_app` is kept when it is empty. The dashboard and the AI never have to think about projects for a single app.
- **A database is an app, not a service of another app.** A service-template app is a worker app with its own deployments, logs, variables, volume, backups and limits, so every existing tool works on it, and `quota_apps` counts it (the default stays 10: a web app and its database are 2). Phase 4's `update_service` and `remove_service` are therefore `update_app` and `delete_app`.
- **The project network is lazy.** `bp-p-<id>` exists only while the project has two apps or more: a project of one app has nobody to talk to, and Docker's address pool (/24s from 10.200.0.0/16) is shared with the app networks. The reconciler creates, wires and removes project networks; joining one does not change a container's config hash, so it never restarts a running service.
- **Aliases on the project network.** A single app's container gets its alias; an app with several services gets `<alias>-<service>` for each and the bare alias on its public service, so `web` reaches the main service of the app `web`.
- **References resolve at container start, not at set time.** The stored value stays `${{db.DATABASE_URL}}`, so a changed password or a renamed alias reaches every app at its next start without rewriting secrets. `set_env` still checks the reference, so a typo is an error at once. A shared variable (no `service`) is what a reference reads. Depth is capped at 3.
- **Only template apps are waited for.** A deployment whose references name a template app waits up to 5 minutes for it to run; references between two apps with their own source are not waited for, which would deadlock when two apps refer to each other.
- **A move is refused while references cross projects** (`app_referenced`, `app_has_references`): the variables would point at nothing after the move. A rename rewrites them instead, and restarts the apps that had them.
- **Templates run as non-root with alphanumeric passwords.** PostgreSQL, MariaDB, MySQL, Valkey and Redis run as 999:999 (the images' own user), Meilisearch as 10001:10001; data lives in `/data` (subfolders where the image needs it). Passwords are 32 characters of `[A-Za-z0-9]` so they need no escaping in a URL. Valkey is the default cache; `redis` is hidden from the list and only taken by name. MinIO is left out (licence and image changes); Garage later.
- **Lists stay `Page[T]`.** The Phase 4b contract wrote `GET /projects` and `GET /service-templates` as bare arrays; they return `{items, next_cursor}` like every other list.
- **Multi-service catalog entries make a project.** An entry with `Services` creates a project named after the app, adds the services, then the app; any failure removes the whole project, so a refused deploy leaves nothing behind.

## Projects: closing the gaps (2026-11-05)

- **Deleting an app that others refer to is refused.** `DELETE /apps/{app}` and `delete_app` answer 409 `app_in_use` while another app in the project has a variable with `${{alias.VAR}}` on it: `details.dependents` is `[{slug, alias, vars}]` (sorted by slug, vars sorted), `next` is `set_env`, and the hint tells the AI to change or unset those variables, or delete those apps, then call `delete_app` again. Deleting the whole project (`with_apps`) is not refused: everything goes. `app_referenced` (a refused move) carries the same `dependents` detail besides `apps`.
- **Renaming a referenced alias rewrites the references** (unchanged behaviour, now the documented choice): the apps that refer to it get their stored values rewritten in the same transaction and are restarted. An `alias_in_use` refusal would only make the AI do the same rewrite by hand.
- **Catalog deploys take `project` and `alias`.** An empty `project` makes a new project named after the app (as before); a given one must be the actor's (`project_not_found` otherwise, also for another user's project). Service aliases of a multi-service entry that are taken get a `-2`, `-3` suffix, and the app's variables are rewritten to the new aliases, so a second WordPress in a project gets `db-2`. An explicit `alias` for the app that is taken is a 409 `alias_taken`: the caller chose it. A failure removes what the deploy made (the new project, or the app and its services in a given project).
- **Names on a project network are checked as a whole.** An alias may not equal an `<alias>-<service>` name of an app with several services and the other way round (create, add_service, update alias, move, catalog): 409 `alias_taken` with `details.name` and `details.app`; default aliases skip taken names. A compose deploy whose services would make a taken name fails validation with 422 `network_name_taken` (`details.service`, `name`, `app`).
- **The restarts of `connect_to` apps are stored** (migration 00250, `deployment_restarts`), taken when the service's deployment goes live and dropped when it fails. At boot, rows of a deployment that went live are restarted, rows of a failed one are dropped, and rows of one still running wait for it.
- **`${{…}}` in a compose file is refused** with `compose_reference_unsupported` per service and key; the hint says to `set_env NAME=${{…}}` on the app and write `${NAME}` in the file. The value then resolves at container start, also inside `environment`, `command` and `healthcheck`. Filling references into the file itself would put secrets into the stored spec.
- **Template versions are shown, never applied.** An app from a service template has `template_latest` (the template's version in this bitploy) and `template_update_available`; get_app's summary says the newer version is not applied automatically. A new major version of a database can need a dump and restore, so upgrading stays the user's step.
- **Manual backups cover every volume.** `create_backup` without `volume` backs up each attached volume of a compose app, one after the other under the app's backup lock (`backups` in the result lists them); `volume=` picks one. `POST /apps/{app}/backups` keeps its shape (one backup, `?volume=`, default the first volume) for the dashboard. Scheduled backups already covered every volume.
- **Project networks drop strangers.** Every wiring of a project network (each project change and at boot) disconnects members that are no container of an app in the project, so an app whose unwiring failed (Docker down, a crash) cannot keep reaching it. Members are read before the apps are listed, so a container attached in between is never taken off; if listing any app's containers fails, nothing is pruned.

## Database dump backups (2026-11-06)

- **A running PostgreSQL, pgvector, MariaDB or MySQL service is backed up as a dump; everything else stays a tar of the volume.** The paused tar of a database's files is already crash-consistent, but a dump is smaller, readable outside bitploy, works across versions, and proves the data reads back. Manual and scheduled backups pick the format the same way (`backupFormatFor`): a dump when the app is a single-container template app with a dump engine and its container runs, otherwise a volume tar (a stopped database's files are consistent). Retention, the storage allowance (`limitWriter` and `commitBackup`) and the backup lock are the same as for volume backups. Migration `00260` adds `app_backups.format` (`volume` | `dump`, default `volume`) and `tool` (the dump tool's `--version` line). Dumps are stored as `<backups>/<app>/<id>.sql.gz` and download as `<slug>-<time>-<kind>.sql.gz`; the API returns `format`, `tool` and, on the list, `dump_tool`.
- **The dump runs inside the database container through `docker exec`** (`dockerx.Exec`: stdin streamed in, stdout streamed out through gzip, the last 4 KiB of stderr kept for the error message). Exec inherits the container's environment, so **passwords never reach a command line**: PostgreSQL gets `PGPASSWORD` exported inside the `sh -c` script from `$POSTGRES_PASSWORD`; MariaDB and MySQL get a `mktemp` option file written with the shell builtin `printf` (no process with the password in its arguments) and removed by a trap. The scripts are constants; nothing user-supplied is put into them. A dump only counts when its end holds the tool's trailer (`PostgreSQL database cluster dump complete`, `-- Dump completed`), so a dump cut short by a crash or a full disk is a failed backup, not a broken file. Docker cannot kill an exec; when a backup is cancelled its streams are closed, which ends the tools on their next write.
- **PostgreSQL: `pg_dumpall` over 127.0.0.1 as `$POSTGRES_USER`**, so roles, every database and their grants are in one file. Restore connects to `template1`, drops every database but the templates (`WITH (FORCE)`, which ends open connections), makes an empty `postgres`, reassigns and drops every other non-`pg_` role, then replays with `psql -v ON_ERROR_STOP=1`. `pg_dumpall` always writes `CREATE ROLE <current user>`, which already exists; a Go filter drops exactly that line in the roles section (before the first `\connect`), so every other error still stops the restore.
- **MariaDB and MySQL dump the user databases, not `--all-databases`.** `mariadb-dump` / `mysqldump --single-transaction --routines --events --triggers --hex-blob --add-drop-database --databases <every database but mysql, information_schema, performance_schema, sys>` (MySQL also `--set-gtid-purged=OFF`). Replaying the `mysql` system schema into a running server is unreliable (MySQL 8.4 refuses parts of it, `--add-drop-database` on `mysql` fails) and the users are the template's generated ones anyway, so users and grants are not in the dump; the root password and the app user from the template's variables stay as they are. Restore drops those user databases and replays with `mariadb` / `mysql --binary-mode`.
- **A dump restore keeps the database running.** It needs the database to run (409 `database_not_running` otherwise, with the hint to start it) and holds the app lock and the backup lock throughout. It first makes a "before restore" dump of the current databases (if that fails nothing is touched), then cleans and replays. If the replay fails, the before-restore dump is replayed the same way and the message says whether the old databases are back. The app is never stopped (`app_restarts` false), so apps connected to it lose their connection for a moment and can briefly see a half-restored database; stopping them would mean reaching into other apps, which a restore of one app should not do. The restore marker on the app row is reused: after a crash a dump restore with a before-restore dump is undone by replaying it, and the app is never kept stopped for it. A volume backup of a database (made while it was stopped, or an upload) still restores the files with the app stopped. A dump cannot be restored into an app that has no dump engine (`dump_not_restorable`).
- **Valkey, Redis and Meilisearch have no backups.** They keep a cache or a search index that can be rebuilt, so backing them up only costs storage (`servicetpl.Template.Backups` is false for them). Back up now, upload and a schedule other than off are refused with 409 `backups_not_needed` (the message names the reason, the hint points to the database the data comes from); the scheduler skips them even with a schedule set from before. The app JSON has `backups_supported`; the dashboard shows one line instead of the backups section, and get_app's summary leaves backups out. No such backups existed when this was decided, so nothing special is kept for old ones.
- **MCP still has no restore tool** (see the backups decision above). `create_backup` and `list_backups` work for database services unchanged and describe the dump format; the new error codes come with hints.

## Public ports (2026-11-06)

- **A forwarder container, not a published port on the app.** `bitploy port-proxy` runs in `bitploy-port-<app id>` from the database helper image (busybox with the bitploy binary, already built for the SQLite viewer), joins only `bp-<slug>` and forwards to the service alias (`app:5432`). Publishing on the app container would mean recreating it (a database restart) on every open and close, and would put a published port on user code; a forwarder on the host network would break the "no host network" rule and could reach every app. The forwarder runs as nobody with no capabilities, `no-new-privileges`, a read-only root, 64 MB, 64 processes, 0.25 CPU and at most 64 connections; it carries no `nl.bitploy.app_id` label, so the app container cleanup, the event watcher and the metrics never see it. A settings hash in a label tells whether a running forwarder still matches; a new bitploy binary gives a new image and so replaces every forwarder once (a few seconds without the port).
- **Only for apps without a web address.** A single web app (and the public service of a compose web app) is refused with `public_port_web_app`: a raw port would go around HTTPS, the Cloudflare proxy and password protection. Service templates, workers and the other services of a compose app may.
- **The port number is stable while open.** The lowest free port of the range is picked in an immediate transaction with the per-user count, `public_ports.port` is UNIQUE, and the row keeps it until the port closes. A port that another program holds on the host (Docker says "port is already allocated") is skipped for 10 minutes and the next one is tried (up to 3 times). When the admin changes the range, the reconciler moves open ports into it (audit `app.public_port_moved`); when the range is removed, it closes them all (reason `public_ports_off`).
- **The expiry is enforced twice.** The forwarder gets `--until` and closes its listener and every connection at that time by itself, so the port closes on time even when bitploy is down; after the expiry it stays idle (no restart loop) until the reconciler removes it and the row with an audit row (reason `expired`). Both read `expires_at` from the database, so a restart changes nothing.
- **The allow list is IPv4 only, and so is the port.** The forwarder is published on `0.0.0.0` only: through Docker's IPv6 proxy every client would arrive with the bridge address, and neither the allow list nor the firewall could tell them apart. `only_my_ip` takes the request's address as `auth.ClientIP` sees it (Cloudflare and our proxies skipped); from IPv6 it is refused with `my_ip_not_ipv4` and a hint to type the IPv4 address. Through MCP that address is the MCP client's, which is right for Claude Code or Cursor on the user's computer and wrong for a chat app in the cloud; the parameter's description says so.
- **The address is the server's IP.** `BITPLOY_PUBLIC_PORTS_HOST`, else `BITPLOY_SERVER_IPV4`, else the edge host. The apps domain is proxied by Cloudflare, which only carries HTTP(S), so `<slug>.<apps domain>:30000` would not connect.
- **Showing the password is an exception to "nobody can read env var values back".** The dashboard and `get_app` show the connection URL with `********`; `POST …/public-port/reveal` (and MCP `show_password`) returns it with the password and the template's other generated secrets. Only the owner (deploy scope or a session; admins get `app_not_found` for other users' apps), only while the port is open, only for service-template apps, and every call is audited. A deploy token could already read these values by deploying an app with `${{db.DATABASE_URL}}` and printing it; this makes the path short and visible instead.
- **The firewall opens only the range.** Docker DNATs a published port in PREROUTING, so the traffic goes through FORWARD and DOCKER-USER, not INPUT: a host firewall like ufw never sees it. `BITPLOY-APPS` now passes DNATed traffic from outside the pool to the pool only when its original port (`--ctorigdstport`) is in the range, or 80/443 (Traefik, in case Docker maps them to an app network address), and drops any other published port into the pool. The range comes from the environment or `/etc/bitploy/bitploy.env`; a bad value opens nothing and the rest of the rules still apply. One app cannot use another app's public port through the server's address: after the DNAT it is pool-to-pool traffic, which the existing 10.0.0.0/8 rule drops.
- **Limits and audit.** `BITPLOY_PUBLIC_PORTS_PER_USER` (3) open per user, counted over the user's apps; admins see the range and every open port and can close any (`DELETE /admin/public-ports/{app}`, reason `admin`). Audit rows: `app.public_port_opened`, `_changed`, `_closed` with a reason (`closed`, `expired`, `admin`, `app_deleted`, `public_ports_off`), `_moved`, `_revealed`; the password is never in one. Deleting an app closes its port first (its forwarder is on the app network); a rename removes the forwarder before the old network goes and starts it on the new network with the same port.
- **Migration 00270** (`public_ports`, one row per app with an open port, `ON DELETE CASCADE`). The number leaves room for the database dump backups work running in parallel.
- **Not verified here (no Docker on this machine):** the forwarder container itself, the Docker port binding and the `ErrPortInUse` detection, the firewall rules and the new probe-test checks. `internal/dockerx/portproxy_integration_test.go` and `deploy/probe-test.sh` cover them and must run on a Docker host (CI runs probe-test.sh). The service logic, the forwarder's Go code (allow list, expiry, connection limit, half-close) and the API are covered by unit tests.

## Agents and static sites; a viewer for database apps (2026-11-06)

- **A static site needs no Dockerfile, in every build mode.** Six agents (Haiku) deployed example apps through MCP; the two static sites each wrote an nginx Dockerfile, because `create_app` makes build mode `dockerfile` and the rules said every app needs one. Those sites then ran as normal apps (512 MB, counted in the quota). `deploy.PlanBuild` in mode `dockerfile` now asks the `auto` rules when the source has no Dockerfile, and takes the answer only when it is a static kind (`static`, `node-spa`, `node-static`): plain website files, or a front end that builds to files. A server without a Dockerfile still gets `dockerfile_missing` with its template, a Dockerfile in the source is always built, and compose detection stays with `auto` only. This replaces "dockerfile mode ignores all of this" for static sites. `deploy_files` passes the planned kind to the early quota check, so a free site is not refused because the memory allowance is full. The MCP instructions (rule 1), the runtime contract and `deploy_files` say to send a site without a Dockerfile.
- **The Database tab opens the server of a PostgreSQL, MariaDB or MySQL app.** The same endpoints and the same UI as the SQLite viewer (`dbview` request and answer shapes); for such an app `path` is a database name on the server (empty: the one in `POSTGRES_DB`, `MARIADB_DATABASE`, `MYSQL_DATABASE`). The helper (`bitploy db-helper`, the same image) runs as nobody with no capabilities in the network namespace of the database's container (`NetworkMode: container:<name>`), so it reaches the server at 127.0.0.1 and nothing that container could not reach already; no port is published and bitploy itself joins no app network. The login comes from the app's own variables: PostgreSQL's user (a superuser in the official image), root for MariaDB and MySQL, like their dump backups. Values are read as the server's text (pgx simple protocol, MySQL text protocol with interpolated arguments) and sent back as text literals, so timestamps, numerics and uuids survive a round trip; a row's key is its primary key, tables without one and views are read-only. Reads run in a READ ONLY transaction that is rolled back, and a read-only console takes only SELECT, WITH, SHOW, EXPLAIN, TABLE, VALUES (and DESCRIBE on MySQL, never INTO OUTFILE/DUMPFILE); everything else needs write (the deploy scope). A stopped database answers `db_not_running`, a changed password `db_login_failed`.
