I've finished the read-only audit; no files were changed. Overall the core deploy loop, projects, service templates, backups/dumps, public ports and the database viewer are solid and well documented. The biggest gaps are what happens after a deploy: nothing tells anyone when something breaks, there is no way to run a command or a scheduled job, automatic backups are off by default, and parts of the MCP surface (descriptions, error hints, missing tools) lag behind what the service layer can already do.

## Top 10 recommendations (impact / effort)

1. **Turn automatic backups on by default and add an MCP tool to set the schedule** (high / S). `backup_schedule` defaults to `'off'` (`internal/store/migrations/00080_app_backups.sql:20`). Nothing changes that for `add_service` databases or catalog apps (Vaultwarden, Forgejo…), and MCP has no tool to change it (`PUT /apps/{app}/backup-settings` is dashboard-only). A beginner who says "make sure this is backed up" gets one manual `create_backup` and nothing after. Default to nightly, keep 7, for volume apps and dump-capable services. Risk: backups use the same disk and count against storage; the "skipped, shows why" handling already exists (`internal/app/backups_sched.go`).
2. **`query_db` already works on PostgreSQL/MySQL/MariaDB, but the tool says it is SQLite-only** (high / S). `dbCall` sends service-template apps to `dbServerTarget` (`internal/app/db_viewer.go:337`). Yet the `query_db` description, the `path` field ("SQLite file inside /data", required) and the rules (`internal/mcp/rules/rules.go`, Databases section) say SQLite only. For "show me the database rows" on a Postgres app, the AI will conclude it can't, or open a public port.
   - Fix the description so `path` means the database name.
   - Split it into a read-only tool and a write tool. It is annotated `destructive()` (`internal/mcp/tools.go:1027`), so clients ask for approval on every SELECT.
3. **"Healthy" only means "the container is running"** (high / S–M). `Healthy = status=="running" &amp;&amp; problem==""` (`internal/mcp/results.go:173`), with no HTTP probe after the deploy check. An app answering 500/502 on every request reports healthy, so "why is my site down?" ends with "it's running fine".
   - Put the last 15 minutes of 5xx rate and answer time (traffic data already exists, `GET /apps/{app}/traffic`) in `get_app`/`list_apps`, plus a `get_traffic` tool.
   - Flag a referenced dependency that is crashed or stopped (web is "healthy" while its `db` is down).
4. **Notifications for deploy failed, crash loop, storage at 80/100%, domain failed and backup failed** (high / M). There is no outbound email or webhook anywhere, only live events in the dashboard. Push-to-deploy failures and crash-loop stops (`internal/metrics/events.go`) go unseen. Security: outbound webhooks from the bitploy container are an SSRF risk (it holds docker.sock and can reach the internal entrypoint and 169.254.169.254). Resolve and block private ranges, or send from a firewalled helper; SMTP settings need encryption like the other secrets.
5. **One-off commands (`run_command` MCP tool and a dashboard console)** (high / M). Today you cannot run `manage.py createsuperuser`, `artisan`, a seed or a migration without baking it into CMD. `dockerx.Exec` exists but is only used for dumps. Run it in a throwaway container from the current image with the same limits, network and volume, rather than exec'ing into the live one. Risk: output can echo secrets, so cap output, add timeouts, require the deploy scope and audit every call.
6. **Scheduled jobs (cron), built on #5** (high / M). There is no cron today; the only hint is the "cron-like loop" note on the worker type (`internal/mcp/tools.go:53`). The AI will build a 512 MB always-on worker. In the meantime (S): add a rules entry saying to use an in-process scheduler in the existing app, and lower worker memory. Risk: CPU and memory use while a job runs must count against quota; limit how many run at once.
7. **Build-time variables** (high for beginners / S–M). `--build-arg` exists only for compose (`internal/deploy/build.go:62`, `internal/app/services.go:52`). A static Vite/Next front end that needs `VITE_SUPABASE_URL`/`NEXT_PUBLIC_*` has no way to set it: `.env` is excluded, and writing a Dockerfile makes the site non-static. The node-spa README even says "`set_env` does not reach a static site" (`internal/templates/node-spa/README.md:8`).
   - Add `build_env` for public values and BuildKit `--secret` for private ones.
   - Risk: build args stay visible in `docker history`, so secrets must go through `--secret` and never be cached on the shared builder.
8. **Let MCP use `auto` builds, and add the missing fields to the dashboard** (high / S).
   - MCP: the `build_mode` enum excludes `auto` (`internal/mcp/tools.go:382,417`). So "put my GitHub repo online" for a Node server with no Dockerfile dead-ends with `dockerfile_missing`, whose hint is "commit and push a Dockerfile". That is impossible when it isn't the user's repo or the AI has no checkout, yet the dashboard's auto mode builds the same repo.
   - Dashboard: there is no field for port, health_path, type, dockerfile_path or context_dir (`web/src/pages/app/SettingsTab.vue` only sends name/slug/domain/memory/cpu/build_mode). `port_unknown`/`port_ambiguous` hints name `update_app`, `friendlyError` hides them, and dashboard users are stuck.
9. **MCP OAuth** (high for beginners / M–L). Connect AI offers only Claude Code, Claude Desktop (via `mcp-remote`, which needs Node), Cursor and VS Code (`web/src/lib/mcp.ts`). The Claude.ai and ChatGPT web connectors need OAuth, and SPEC lists it as "Next after v1". Risk: consent phishing; map grants to the read/deploy scopes and consider per-project tokens.
10. **Moving an app that is connected to a database deadlocks** (medium / S–M). Moving `web` fails with `app_has_references`; moving `db` fails with `app_referenced`, whose hint says "or move those apps too" (`internal/app/projects.go:667-676`), which can never succeed. The UI has the same single-app move (`web/src/pages/app/ProjectSettings.vue`). Allow moving a group (`update_app project` with a list, or move the dependencies along) and fix the hint.

## Everything else

**Features**
- **Preview environments per PR** (L): SPEC "Next after v1". Needs `pull_request` events, quota per preview and a TTL. Risk: fork PRs running with the app's secrets; make previews owner-only with secrets off by default.
- **Shared project variables** (S–M): only per-app variables plus `${{alias.VAR}}` exist (`ProjectVariablesTab.vue` only lists them).
- **Database template upgrades** (M): versions are frozen ("no upgrade tool", `internal/mcp/results.go:387`). Patch releases (18.6 to 18.7) are security fixes and could update safely after a dump. Catalog updates exist in REST/UI (`POST /apps/{app}/catalog-update`), but MCP has no tool for them and doesn't mention `catalog_update`.
- **Logs** (S–M): runtime logs come only from the current container (`internal/app/apps_logs.go`), and `restart_app` recreates the container, so crash logs vanish once the AI restarts. Keep the previous container's last lines; no retention or export beyond the 10 MB×3 rotation.
- **Per-app or per-project tokens and a deploy hook URL** (S): tokens are read/deploy across every app (`internal/app/accounts_tokens.go`). CI and non-GitHub hosts (the Forgejo in the catalog included) get no push-to-deploy. Both reduce how much a leaked token can do.
- **Off-site per-app backups (S3)** (M): app backups stay on the same disk (README "Backups"); `deploy/backup.sh` is for admins only. No PITR or connection pooling; fine to skip.
- **Teams / shared projects** (L): a SPEC non-goal. Projects are per user (`projects.go`, `p.UserID != row.UserID`). It matters for "group of colleagues" but means a new authorization model.
- **Smaller items** (S each): secret files mounted into the app (env values cap at 32 KB); www/apex redirect for custom domains (none in `internal/proxy`); Python/Go autodetect only matters for the dashboard and GitHub path; the template marketplace is a fixed 27 entries with no starter projects. Replicas and autoscaling don't fit one server.

**MCP flow gaps (each S)**
- **Variables:** there is no `list_env` tool (the REST `listEnv` exists). The AI can't check which variables are set while debugging "missing env var"; the only workaround is `set_env` with an empty body, which needs a deploy token.
- **Dashboard-worded hints reaching the AI:** `file_not_found` says "Reload the list" (`internal/app/volume_files.go:240`); `db_not_found` says "Pick one of the databases in the list" and points back to `query_db` (`internal/mcp/server.go` `defaultNextTool`), which invites guessing loops. There is no MCP tool to list /data files, so the AI has to guess the SQLite path when it can't see the code.
- **"Connection string to debug":** this depends on `BITPLOY_PUBLIC_PORTS`, which is off by default, so the AI hits `public_ports_off` and can only "ask the admin". Point it at `query_db` (once #2 is fixed) as the first choice. `only_my_ip` is wrong for cloud clients; the description already says so.
- **Rollback:** the result doesn't say that the next push with auto-deploy rebuilds the broken commit, or that env and data are not rolled back (`internal/mcp/results.go:586`).
- **Missing tools:** schedule, traffic, catalog update, project rename/delete, a specific deployment's full build log (`get_logs` gives only the latest build, `get_deployment` 50 lines), and `home_page`/`output_dir` in `create_app`.
- **Restore** is dashboard-only on purpose. Consider a restore with a typed confirmation, since `query_db write=true` can break data that the AI then can't put back.

**Rough edges and docs drift (each S)**
- **Health check timeout:** SPEC says "within 60 s (max 300 s)" (`SPEC.md:194`), but the code has a fixed `healthTimeout = 60s` with no setting (`internal/app/deploy_pipeline.go:38`). Slow starts (Java, migrations at boot) fail.
- **SPEC is behind the code:**
  - It says "no buildpack or auto-detect build path" (`SPEC.md:159,768`), while auto mode builds Node and static sites.
  - It lists "Raw TCP ports" as not in v1 (`SPEC.md:769`), while public ports ship.
  - README line 6 promises Node builds without a Dockerfile, which MCP can't do (rule 1 in `instructions.md`).
- **Dashboard-only, for no clear reason:** backup schedule, traffic, catalog update, env names, project rename/delete.
- **MCP/REST-only, for no clear reason:** port, health_path, type, dockerfile_path, context_dir.
- **Code markers:** only one TODO in the codebase, in vendored chart UI. The known gaps listed in `docs/compose-plan.md` ("Known gaps") are minor.
